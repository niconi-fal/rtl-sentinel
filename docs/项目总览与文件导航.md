## 一、这个 Agent 能做什么

### 1. 静态审查 Verilog / SystemVerilog 代码（13 条规则）

零第三方依赖，一条命令即可运行，**不依赖任何商业 EDA license**。

| ID | 规则 | 严重度 | 说明 |
| --- | --- | --- | --- |
| R001 | 推断锁存器 | warning | 组合块分支未覆盖全；识别 `(* full_case *)` 属性 |
| R002 | 位宽截断 | error | 含**常量值位宽推断**与**表达式位宽推断**（加法不自动扩位） |
| R003 | 时序块误用阻塞赋值 | warning | 块内临时变量自动豁免 |
| R004 | 多驱动 | error | 识别 generate 互斥分支、位分段驱动 |
| R005 | 敏感列表不完整 | warning | `@*` 自动豁免 |
| R006 | 跨时钟域未同步 | warning | 识别同步器/格雷码命名约定 |
| R007 | 不可综合结构 | 三级 | 延时=error / `initial`=warning / 调试打印=info |
| R008 | 未使用信号 | info | 条件编译块内自动豁免 |
| R009 | 实例端口位宽不匹配 | error | **跨文件**比对端口定义 |
| R010 | 实例端口未连接 | warning | **跨文件**检查漏连 |
| R011 | 组合逻辑误用非阻塞赋值 | warning | 对应 Verible `always-comb-blocking` |
| R012 | 赋值运算符误用 | error | `assign x == y;` 把赋值写成比较 |
| R013 | 实例化连接方式混用 | error | 按名/按位置混用，LRM 禁止 |

### 2. 跨文件工程分析

建立全工程「模块名 → 端口表」索引，因此能检查单文件工具做不到的事：
实例端口位宽是否匹配、端口是否漏连。查不到定义的模块（FPGA 原语、工艺库）保守跳过。

### 3. 大模型语义裁定（默认开启，需配置 API）

对每条规则告警给出：**真伪裁定 + 根因分析 + 最小修复补丁 + 验证方法**。
支持任意 OpenAI 兼容后端（DeepSeek / 通义 / 智谱 / 本地 Ollama）。

### 4. 大模型检测通道（`--llm-detect`，可选）

把大模型作为"检测器"补充规则引擎的漏报。输出标为「待复核 · LLM 线索」，
**不计入风险分、不进 CI 门禁** —— 因为它不可复现。

### 5. 豁免机制

集中式 `.rtlsentinel.json`，强制带理由、可审计。**豁免不隐藏**（被豁免的告警
仍出现在报告中并注明理由）。

### 6. 五种输出 + CI 集成

Text / Markdown / **HTML**（可截图演示）/ JSON / **SARIF 2.1.0**（接 GitHub Code Scanning）。
退出码约定 0/1/2，可直接做门禁。

### 7. 风险评分与健康分

按代码规模归一化（每千行加权缺陷密度），避免大工程被"绝对数量"冤枉。

## 二、效果怎么样（五套评测，全部可复现）

| 评测轨 | 命令 | 结果 |
| --- | --- | --- |
| **受控样例集** | `python bench/evaluate.py` | 规则级 **21/21**（P/R 100%）+ 定位级 **32/32**（含行号校验） |
| **真实开源语料** | `-m rtl_sentinel.cli bench/corpus` | 42 文件 / 15151 行；告警 **491 → 127**，error **397 → 27（−93%）** |
| **裁定一致性** | `python bench/evaluate_adjudication.py` | 离线 **90.6%**；DeepSeek **89.8%**（「应豁免」类 **99%**） |
| **学术第三方基准** | `python bench/evaluate_lintllm.py` | LintLLM benchmark（90 模块），规则引擎检出率 **23.3%** |
| **对照实验** | `python bench/evaluate_llm_direct.py` | DeepSeek 直接检测 **72.2%**（同一 benchmark 同口径） |

**其他工程指标**

- 单文件静态分析：**2.7 ms**（90 模块仅 18 ms，比 LLM 快约 4500 倍）
- 真实语料应用 14 条豁免规则后：健康分 **17.0 → 79.9**
- 规模：核心包 3303 行 Python + 评测工具 848 行，**零第三方依赖**

**最值得在面试里讲的一个结果**：对照实验显示 LLM 检出率（72.2%）显著高于规则引擎
（23.3%），但两者的**衰减方向相反** —— LLM 在简单模块上 96.7%、复杂模块只剩 33.3%，
而规则引擎不受代码长度影响（complex 档 30.0%，几乎追平）。

## 三、能否改进（四条，都有实验依据）

| # | 改进项 | 依据 | 成本 |
| --- | --- | --- | --- |
| 1 | `generate` 分支语义展开 | 目前只用于抑制表观多驱动，未做分支展开，参数化设计下跨模块检查不完整 | 中高 |
| 2 | 跨模块 CDC 检测 | 现只覆盖同模块内跨时钟域，跨模块需要时钟树与层级视图 | 中高 |
| 3 | 表达式位宽推断扩展到减法/移位/拼接 | 学术 benchmark 显示该类仍有漏检（Bit Width 类只检出 21%） | 中 |
| 4 | 补 Verible 的 `explicit-begin`、`module-filename` 规则 | 规则集与工业工具对齐 | 低 |

**以及一条"不该做"的**：语法/声明类缺陷（未声明信号、中文标点、保留字误用）
在本工具上是 0 覆盖 —— 但那属于 LintLLM 那条路线的疆域，
正确做法是调用大模型而不是继续写规则。
