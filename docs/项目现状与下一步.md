### 1.3 四轨评测（全部可复现）

| 评测轨 | 命令 | 结果 |
| --- | --- | --- |
| **受控样例集** | `python bench/evaluate.py` | 规则级 **21/21**（P/R 100%）+ 定位级 **32/32**（含行号校验） |
| **真实开源语料** | `-m rtl_sentinel.cli bench/corpus` | 42 文件 / 15151 行；告警 **491 → 127**，error **397 → 27（−93%）** |
| **裁定一致性** | `python bench/evaluate_adjudication.py` | 离线 **90.6%**；DeepSeek **88.2%**（「应豁免」类 **99.0%**） |
| **学术第三方基准** | `python bench/evaluate_lintllm.py` | LintLLM benchmark 90 模块，规则引擎检出率 23.3% |
| **外部交叉验证** | `python bench/check_verilator.py` | Verilator 独立复核 R001/R002/R004（需另装；未装则跳过） |
| **对照实验（新增）** | `python bench/evaluate_llm_direct.py` | DeepSeek 直接检测 **72.2%**，同一 benchmark 同一口径 |

工程指标：真实语料应用 14 条豁免规则后，健康分 **17.0 → 79.9**。

**对照实验的核心结论**：在检出率上 LLM 显著占优，但两者衰减方向相反
（LLM 96.7%→33.3%，规则引擎不受长度影响）；在耗时（快 4500 倍）、成本、
可复现性、可进 CI 门禁上规则引擎不可替代。**结论是分层而非替代。**

## 四、如果面试官问"这个项目还能怎么改进"

直接答这四条（都有实验依据，不是空话）：

1. **让 LLM 参与检测通道** —— 对照实验显示 LLM 检出率 72.2% 显著高于规则引擎 23.3%，
   值得作为"减少漏报"的补充；但必须标注为"待复核"、不进 CI 门禁，
   以保留可复现性。
2. **`generate` 分支语义展开** —— 目前只用于抑制表观多驱动，未做分支展开，
   因此参数化设计下的跨模块检查仍不完整。
3. **跨模块 CDC 检测** —— 现只覆盖同模块内跨时钟域，跨模块需要建立时钟树与层级视图。
4. **规则覆盖的边界** —— 学术 benchmark 实测显示，本工具在语法/声明类缺陷上是 0 覆盖，
   那属于 LintLLM 那条路线的疆域；若要补齐，正确做法是接入 LLM 而非继续写规则。
