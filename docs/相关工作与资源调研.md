## 一、最重要的发现：LintLLM —— 直接对标的学术工作

**LintLLM: An Open-Source Verilog Linting Framework Based on Large Language Models**

| 项 | 内容 |
| --- | --- |
| 会议 | GLSVLSI 2025（ACM） |
| 代码 | https://github.com/fangzhigang32/Static-Verilog-Analysis （MIT） |
| 论文 | arXiv:2502.10815 |

### 它的方法

1. **Prompt of Logic-Tree** —— 11 步结构化提示，引导 LLM 按树式逻辑逐层推理：
   标点 → module 结构 → 语句结尾 → 变量（方向/类型/位宽/使用）→ always 块
   （类型/敏感列表/赋值方式）→ begin-end → 保留字 → 竞争冒险 → case → 实例化 → 运算符
2. **Defect Tracker** —— 三步算法识别"根因缺陷"，抑制同一根因衍生的多条次级报错，降低冗余
3. **Benchmark** —— 90 个 Verilog 模块 × 11 类注入缺陷，分 simple / medium / complex 三级

### 它的结果

| 工具 | 正确率 ↑ | 误报率 ↓ |
| --- | --- | --- |
| 商业 EDA | 64.44% | 27.78% |
| Verilator | 62.22% | 32.22% |
| **o1-mini + LintLLM** | **83.33%** | **12.22%** |

成本：检测 100 万行 ≈ $20（不到商业工具的 1/10）。

### 与本项目的关系

这是**最直接的对标工作**，差异恰恰是最有价值的部分：

| 维度 | LintLLM | RTL-Sentinel |
| --- | --- | --- |
| 缺陷发现 | LLM 直接检测（逻辑树提示） | **确定性规则引擎** |
| LLM 的角色 | 检测器 | **只做裁定与解释，禁止发明新告警** |
| 可复现性 | 依赖模型与提示，存在随机性 | 规则层零随机、可复现 |
| 跨文件分析 | 单文件 | **跨文件模块索引**（R009/R010） |
| 覆盖倾向 | 全覆盖轻量检查（含语法/声明类） | 可综合设计缺陷**深度**检查 |

**核心判断**：LintLLM 让 LLM 承担"缺陷发现"并做到 83.33% 正确率；本项目主张
**可形式化的缺陷应由确定性规则发现**。两条路线不矛盾，而是互补 ——

- **语法 / 声明类**缺陷（未声明信号、保留字误用、中文标点）→ LLM 天然擅长，规则实现成本高
- **符号计算类**缺陷（位宽算术、多驱动、CDC）→ 规则零误报，LLM 受 tokenization 影响不可靠

我把这个判断**做成了可验证的实验**（见第四节）。

## 二、工业级 Lint 工具的规则集（最有用的参考）

### Verible（Google 发起，Chips Alliance 维护，Apache-2.0）

https://github.com/chipsalliance/verible ｜ 约 60 条 lint 规则

与本项目规则的直接对应：

| Verible 规则 | 含义 | RTL-Sentinel |
| --- | --- | --- |
| `case-missing-default` | case 缺 default | R001 推断锁存器 |
| `truncated-numeric-literal` | 数字字面量被截断 | R002 位宽截断 |
| `always-comb-blocking` | 组合逻辑用非阻塞赋值 | **R011（本次新增）** |
| `always-ff-non-blocking` | 时序逻辑用阻塞赋值（带 `waive_for_locals` 开关） | R003（`block_local_temp` tag 与之同思路） |
| 外部 waiver 文件机制 | 集中式豁免 | `.rtlsentinel.json`（设计一致） |

**两个重要确认**——我的设计决策与工业工具不谋而合：

1. Verible 的 `always-ff-non-blocking` 提供 `waive_for_locals` 参数，
   正是我判定"块内临时变量应豁免"的做法；
2. Verible 同样提供**外部 waiver 文件**机制，说明集中式豁免是工业标准而非我的独创。

**可直接借鉴、本工具暂无的规则**：`explicit-begin`（多语句分支必须 begin-end）、
`module-filename`（模块名与文件名一致）、`dff-name-style`（触发器命名约定）、
`endif-comment`、`mismatched-labels`、`no-tabs` / `line-length`（纯风格类）。

### svlint（Rust，393★）
https://github.com/dalance/svlint —— SystemVerilog linter，规则集参考 Verible 并扩充。

## 三、可替代自研模块的成熟组件

| 项目 | 语言 | 价值 | 是否采纳 |
| --- | --- | --- | --- |
| [Surelog](https://github.com/chipsalliance/Surelog)（476★, Apache-2.0） | C++ | SystemVerilog 2017 完整预处理/解析/elaborate + Python AST API | **未采纳**：引入原生依赖 |

| [pysvinst](https://github.com/sgherbst/pysvinst)（27★） | Python | 专解析模块定义与实例化 | 思路与我的 `index.py` 一致，可做交叉验证 |

**结论**：这些组件质量很高，但都会引入第三方依赖。
本项目「零依赖、任意环境一条命令可跑」的定位在**演示与教学场景**价值更大，
因此暂不替换，但记录为未来"高精度模式"的候选后端。

## 四、在 LintLLM benchmark 上的实测（本次调研的核心产出）

已把 benchmark 导入 `bench/thirdparty/lintllm/`，人工转录其 GT 表为
`GROUND_TRUTH.json`，用 `bench/evaluate_lintllm.py` 评估。

### 结果

```
benchmark  : 90 个模块 / 11 类注入缺陷
本工具告警 : 80 条
模块级检出率 : 23.3%  (21/90)
告警精确率   : 27.5%

按缺陷类型
  Sensitivity List                44%    ← 本工具覆盖较好的
  Module Instances                38%
  Reserved words                  33%
  Operators                       29%
  Port Type                       25%
  Signal Usage                    23%
  Bit Width Usage                 21%
  Race or Hazard                   9%
  Syntax Structure                 0%    ← 本工具未覆盖
  Logic Synthesis                  0%
  Combinational or Sequential      0%
```

### 三条结论

**① 定位差异被量化了。** 本工具在"可综合设计缺陷"上有效
（敏感列表 44%、实例化 38%、运算符 29%），在"语法与声明类"上基本无覆盖
（Syntax Structure / Logic Synthesis / Combinational 均为 0%）。
这印证了第一节的判断：两条路线各有疆域，不是谁替代谁。

**② 发现并修复了一个真实盲区。** Bit Width Usage 初测只检出 14%，
根因是 R002 **对表达式一律跳过**。但 Verilog 的算术运算符不会自动扩展位宽 ——
`a + b` 的结果位宽是 max(width(a), width(b)) 而非 max+1，
所以 `reg [3:0] sum; assign sum = a + b;` 会静默丢失高位。
补上保守的表达式位宽推断后，该类型检出率从 14% 提升到 21%。

**③ benchmark 本身存在方法论局限。** 每个模块**只标注"注入的那一处"缺陷**，
没有标注代码中自然存在的其他问题。因此任何检出额外问题的工具都会被计入"误报"
—— Verilator 32.22% 的误报率有同样成因。这解释了本工具 27.5% 的精确率
为何被显著低估（很多告警指向的是 benchmark 未标注的真实问题）。

## 四之二、对照实验：LLM 直接检测 vs 规则引擎（本轮新增）

上游论文只报告了 LintLLM 的成绩，但没有回答一个更具体的问题：
**"可形式化的缺陷"是否真的更适合交给规则引擎？**

我做了一个正面对照实验：同一套 benchmark（90 模块 / 11 类注入缺陷），
让 DeepSeek **零提示工程**直接读源码指出缺陷行（温度 0），与规则引擎对比。

```bash
RTL_SENTINEL_API_KEY=sk-xxx python bench/evaluate_llm_direct.py --model deepseek-chat
```

### 结果

| 方案 | 模块级检出率 | 来源 |
| --- | --- | --- |
| 商业 EDA | 64.44% | 上游论文 |
| Verilator | 62.22% | 上游论文 |
| o1-mini + LintLLM（逻辑树提示 + Defect Tracker） | 83.33% | 上游论文 |
| **DeepSeek 直接检测（零提示工程）** | **72.2%** | **本次实测** |
| RTL-Sentinel 规则引擎 | 23.3% | 本次实测 |

**三个可以直接讲的观察**

**① LintLLM 的提示工程确实有效。** DeepSeek 零提示是 72.2%，
LintLLM 用 o1-mini + 逻辑树提示 + Defect Tracker 是 83.33%，
**相差 11 个百分点**——这部分增益来自提示方法与根因聚合，而非模型本身。

**② LLM 与规则引擎的衰减方向相反。** 这是最有价值的发现：

| 难度 | DeepSeek | 规则引擎 |
| --- | --- | --- |
| simple | **96.7%** | 23.3% |
| medium | 86.7% | 16.7% |
| complex | **33.3%** | **30.0%** |

代码越长，LLM 衰减越严重（96.7% → 33.3%）；规则引擎不受长度影响。
说明：**LLM 的优势在短代码上最大化，规则引擎的价值在长代码上相对提升。**

**③ 工程指标上两者不可比。**

| 维度 | DeepSeek | 规则引擎 |
| --- | --- | --- |
| 90 模块耗时 | 81.8 s | **18 ms（快 4500 倍）** |
| 成本 | 约 ¥0.1–0.3 | 0 |
| 可复现性 | 温度 0 也不保证一致 | 完全确定 |
| 可否直接进 CI 门禁 | 否（自然语言，需人工复核） | **是** |

### 这个结果对项目意味着什么（诚实的自我评估）

在"检出率"这个单指标上，规则引擎输了。但结论不是"规则引擎没用"，而是：

1. **该 benchmark 偏向 LLM。** 它侧重语法/声明类缺陷（中文标点、未声明信号），
   这类问题"读一遍就能发现"，LLM 天然占优；规则引擎需要为每种模式手写规则。
   DeepSeek 在 Syntax Structure 上 83%、规则引擎 0%，就是这个原因。
2. **算法分工仍然成立。** 规则引擎的核心价值不是"检出率最高"，而是
   **零误报 + 可复现 + 毫秒级 + 可审计**——这是 CI 门禁的硬要求。
3. **一个诚实的开放问题：该不该让 LLM 也参与检测？**
   从数据看值得尝试（至少作为"减少漏报"的补充通道），
   但必须保留规则引擎作为确定性基线，否则整个系统失去可复现性。

<details>
<summary>我对这个结果的判断依据</summary>

我最初做这个实验的目的是**验证**自己的架构判断（规则更适合可形式化缺陷）。
结果部分证伪了这个判断：在"发现缺陷"这件事上，LLM 比我预想的更强。

但进一步拆解后发现两点仍成立：
- 规则的**零误报 + 可复现 + 速度**是 LLM 无法替代的（工程属性，非检出率）；
- 在**长代码**上规则的优势相对提升（complex 档 30% vs 33.3%，几乎持平）。

所以我把结论修正为：**不是"规则替代 LLM"，而是"两者分层"** ——
这也是项目当前的架构（规则发现、LLM 裁定）。这个修正过程本身，
比原先的判断更有说服力。

## 六、保研材料中的引用建议

面试时可以这样表述本项目与 LintLLM 的关系：

> 我的工作与 GLSVLSI 2025 的 LintLLM 是同期、互补的两条路线。
> LintLLM 让大模型直接做缺陷检测，靠"逻辑树提示"把正确率做到 83.33%；
> 我的判断是 —— 可形式化的缺陷（位宽算术、多驱动、CDC）应交由确定性规则，
> 因为这类判断本质上是符号计算，LLM 的 tokenization 会破坏位级语义，且结果不可复现。
> 所以我做的是"规则引擎负责发现、LLM 负责裁定与解释"的双引擎架构。
>
> 我也在其公开 benchmark 上做了第三方评估，量化了两者的适用边界：
> 在可综合设计缺陷上我的规则有效（敏感列表类 44%），
> 在语法与声明类缺陷上确实不如 LLM（0%）。
> 这个结论让我更清楚工具的边界在哪，也说明我没有闭门造车。

这段表述体现四点：**了解前沿、有独立技术判断、做过实测验证、能诚实界定边界**——
比单纯罗列功能更有说服力。
