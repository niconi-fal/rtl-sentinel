# RTL-Sentinel 项目说明

> 面向集成电路设计的 **RTL 智能代码审查 Agent**
> 技术栈：Python（零第三方依赖）+ 大模型 Agent | 规模：核心代码约 1900 行，Verilog 样例 334 行

---

## 一、一页纸摘要

**做了什么**：实现了一个可以直接对 Verilog 源码做静态审查的工具，能自动检出
8 类典型 RTL 缺陷（latches 推断、位宽截断、阻塞赋值误用、多驱动、敏感列表不全、
跨时钟域未同步、不可综合结构、未使用信号），并给出根因分析与修复补丁。

**核心判断**：代码审查中"发现问题"与"解释问题"是两类不同性质的任务。
前者是符号计算（位宽算术、数据流追踪），必须由确定性规则承担；
后者是语义理解，才交给大模型。因此采用**双引擎架构**，
并在接口上做单向约束——**LLM 只能裁定规则引擎已产出的告警，不允许发明新告警**。

**量化结果**：在自建含 GROUND TRUTH 标注的评测集（9 个文件 / 21 个判定单元）上
取得 **Precision 100%、Recall 100%、F1 = 1.00**；在 3 个真实开源仓库
（42 文件 / 15151 行，含 RISC-V CPU 核）上完成泛化验证，
**告警总数从 491 降至 127，其中 error 级从 397 降至 27（−93%）**；
构造裁定金标准量化语义推理层能力，**离线后端一致率 12.7% → 85.7%（判定单元口径）**，
并主动披露该金标准为自产自评、随附独立盲标工具；接入 DeepSeek 实测后在「应豁免」
语义判断上达到 **99.0%**（告警条数口径）**；
并实现集中式豁免机制与 SARIF 输出以接入 CI（真实语料应用豁免后健康分 17.0 → 79.9）；
最后引入 **GLSVLSI 2025 论文 LintLLM 的公开 benchmark（90 模块）完成第三方评估**，
量化了与纯 LLM 路线的适用边界，并据此补充 3 条规则、修复 1 处真实盲区。
单文件静态分析耗时 **2.7 ms**。

## 二、背景与痛点

RTL 代码审查是数字 IC 设计流程中不可跳过的一环。现有方案各有明显短板：

| 方案 | 问题 |
| --- | --- |
| 商业 Lint 工具（SpyGlass、Ascent Lint） | License 昂贵、个人与小团队难以获得；只报"哪里错"，不解释**为什么错、怎么改** |
| 开源工具（Verilator、iverilog 的 `-Wall`） | 侧重仿真与语法，对 latch 推断、CDC 等设计意图级问题覆盖有限 |
| 直接用大模型审代码 | **在位宽算术与数据流追踪上系统性出错**——tokenization 破坏数字的位级语义；输出不可复现、存在幻觉 |

同时，代码审查中的两类任务在本质上不同：

- **结构性问题判定**（如 `reg [3:0] x; x <= 8'hFF;` 会截断）→ 符号计算，
  需要精确、可复现、能写测试用例；
- **根因归纳与修复**（如"为什么这里不适合用阻塞赋值"）→ 语义理解。

把这两件事都交给同一个机制，无论交给谁都会做砸。这就是项目的出发点。

## 三、技术方案与创新点

### 3.1 双引擎分工架构

```
RTL 源码
   │
   ▼
┌───────────────────────────┐
│ 轻量解析器（自研，零依赖） │  注释剥离保行号 → 模块边界 → begin/end 配平
│                           │  → 语句级定位；产出信号表 / 过程块 / 赋值关系
└───────────┬───────────────┘
            ▼
┌───────────────────────────┐
│ 确定性规则引擎（13 条规则）│  零随机 · 零网络 · 可复现 · 行号精确
└───────────┬───────────────┘
            ▼  告警 + 源码片段（单向）
┌───────────────────────────┐
│ LLM 语义推理层            │  裁定真伪 → 归纳根因 → 生成补丁 → 建议验证方法
│ （可插拔：离线/在线后端）  │  ★ 禁止产生新告警
└───────────┬───────────────┘
            ▼
    Text / Markdown / HTML / JSON 报告
```

### 3.2 四个关键技术点

**① 单向接口约束抑制幻觉**

LLM 的输入被严格限定为"规则告警 + 对应源码片段"，
输出为结构化三元组 `{verdict, reason, patch}`。
代码侧再按 `(rule_id, line)` 做匹配校验，模型返回不存在的告警会被直接丢弃。
幻觉被**结构性排除**，而不是靠提示词祈祷。

**② 位宽检查引入"常量值位宽推断"**

朴素实现只比较两侧声明位宽，抓不到 `reg [3:0] cnt; cnt <= 20;` 这类缺陷
（20 需要 5 位表示）。本项目对无显式位宽的十进制常量按数值所需最小位宽推断，
可检出此类真实流片风险。

**③ 解析器采用启发式管线而非完整语法分析**

不引入 ANTLR/Yacc，用"注释剥离 → 块结构配平 → 语句级正则"实现，
好处是**零第三方依赖、任意环境可运行、对残缺代码不抛异常**
（面向前端 IDE 实时审查场景）。代价是放弃完整语法树表达能力，
但已足以支撑全部 13 条规则。

**④ 跨文件模块索引**

真实 RTL 工程是多文件互连的，单文件分析看不到被实例化模块的端口定义，
导致实例化相关的判断全面失真 —— 实测在 42 文件的真实语料上，
"把实例的输入连接误判成驱动源"一举制造了 200 多条假的多驱动告警。

因此系统先对全工程建立「模块名 → 端口表」索引，再做逐文件审查。
对查不到定义的模块（FPGA 原语如 `SB_SPRAM256KA`、工艺库单元、第三方 IP）
一律**保守不判** —— 宁可漏报，也不制造误报。

### 5.2 真实代码泛化验证

受控样例集只能证明"规则逻辑写对了"，不能证明"在真实代码上能用"。
因此引入 3 个真实开源仓库做泛化验证：

| 仓库 | License | 内容 |
| --- | --- | --- |
| YosysHQ/picorv32 | ISC | 32 位 RISC-V 软核 + picosoc 外设（UART / SPI / Flash 控制器） |
| alexforencich/verilog-uart | MIT | 工业风格 UART 收发器 |
| alexforencich/verilog-axis | MIT | AXI-Stream 基础设施（FIFO / 仲裁 / 位宽转换 / COBS 编解码） |

合计 **42 个文件 / 15151 行** Verilog。首轮审查产出 491 条告警，其中 error 397 条 —— 
这个数量级本身就说明存在系统性误报（成熟开源项目不可能有 397 个致命缺陷）。

**收敛结果**

| 指标 | 首轮 | 修复后 | 变化 |
| --- | --- | --- | --- |
| 告警总数 | 491 | **127** | −74% |
| error 级 | 397 | **27** | **−93%** |
| R004 多驱动 | 215 | 8 | −96% |
| R002 位宽 | 59 | 13 | −78% |
| R007 不可综合 | 111 | 34 | 重新分级 + 按模块聚合 |
| R006 跨域 | 9 | 1 | 识别同步器/格雷码约定 |

**七类误报的根因与修复**（全部为真实代码特有，受控样例集无法暴露）

| 误报现象 | 根因 | 修复手段 |
| --- | --- | --- |
| R004 × 215 条 | 把实例的**所有**端口连接当成驱动源，未查端口方向 | 建立**跨文件模块索引**，仅 output/inout 计入驱动 |
| R004 参数化分支 | `generate if/else` 是互斥分支，静态看像多驱动 | 标记 generate 区间，互斥分支不计 |
| R004 分段驱动 | `assign x[31]=..; assign x[30:23]=..;` 是合法的位分段驱动 | 解析位选区间，无重叠则判定合法 |
| R009 × 35 条 | 参数覆写实例（`#(.W(32))`）改变端口位宽；位选连接被当作整信号 | 两类情形保守跳过 |
| R002 | 位宽表达式含未求值参数时退化为 1 位 | 标记"位宽未知"，跳过而非误判 |
| R002 误报数组元素 | `axis_tdata_pipe[0]` 的 `[0]` 是**数组下标**而非位选，语法完全相同 | 声明时记录数组维度，区分下标与位选 |
| R008 × 31 条 | `ifdef DEBUGREGS` 内声明的调试寄存器 | 标记条件编译区间，自动豁免 |
| R003 × 45 条 | picorv32 刻意用阻塞赋值做块内顺序计算 | 降为 warning，消息说明属设计风格差异 |

**一个真实的解析器缺陷（本次验证最有价值的收获）**

```
if (long_counter_reg <= word_cnt) begin     // 这是"小于等于"比较
    ...
end
```
`<=` 在 Verilog 中**双重语义**：既是非阻塞赋值，又是"小于等于"运算符。
原实现把它误判为对 `long_counter_reg` 赋值，污染了信号驱动集合，制造出假的多驱动告警。

修复方案：用**括号深度**判定 —— 语句顶层是赋值（`x <= y;`），
括号内是比较（`if (a <= b)`）。修改后 R004 从 215 条直降到 8 条。

> 这类语义盲区**只有真实代码能暴露**：自造样例时我天然避开了易混淆写法。
> 受控评测集在每一轮修复后均做回归，**始终 24/24（R001–R013 全覆盖）、Precision 100%、Recall 100%**。

**剩余告警的性质**：修复后的 8 条 R004 全部来自 `spiflash.v`
（SPI Flash 的**行为仿真模型**，用多个 always 块驱动同一组变量模拟器件行为，
并非综合目标代码），告警本身正确。另有 45 条 R003 为上述编码风格提示。
### 5.3 语义推理层的裁定评测

规则层负责"发现问题"，语义推理层负责"裁定真伪、归因、给补丁"。
后者的能力此前从未被量化，因此我人工复核了真实语料上的告警，
构造裁定金标准（43 个 (文件, 规则) 组合 / 126 条告警），度量其裁定准确率。

**裁定标准**：该告警是否指向一个**需要修改的真实问题**。
对成熟开源项目，"技术上正确但设计者有意为之"应判为 `false_positive`（需豁免而非修复）。

| 推理后端 | 一致率（判定单元，42 个） | 一致率（告警条数，旧口径） | 「应豁免」类 | 「无法判定」类 |
| --- | --- | --- | --- | --- |
| 朴素启发式（默认判“确认缺陷”） | — | 12.7%※ | — | — |
| 改进后的离线启发式 | **85.7%** (36/42) | 90.6% (115/127) | 88.1% | **100%** |
| **DeepSeek**（真实 LLM，实测） | **73.8%** (31/42) | 89.0% (113/127) | **99.0%** | 53.8% |

> **口径说明**：金标准为“每个 (文件, 规则) 一个结论”。旧口径按**告警条数**计数，
> 会把同一标注重复计入多次（42 个独立标注被算成 127 条），**系统性抬高数字**；
> 应以**判定单元**口径为准。后两列仍为告警条数口径。该金标准目前为**自产自评**，
> 这是本项目的已知短板 —— 独立盲标流程见第十一节。

※ 朴素启发式口径为 126 条告警的早期版本，列出以说明“默认硬判确认缺陷”的代价。
LLM 有非确定性，多次实测（告警条数口径）在 **88–90%** 波动；离线后端完全稳定。

**接入真实 LLM 后的实验结论（本轮新增的实测数据）**

接入 DeepSeek 后总一致率**并非单调提升**，但拆开看差异极具说明性：

- **LLM 在"语义豁免判断"上明显更强：99.0% vs 88.1%**。
  判断一段代码是"设计者有意为之"还是"笔误"，正是语义理解的用武之地 ——
  人工标注中 101 条"应豁免"的告警，DeepSeek 判对了 **100 条**。
- **离线硬规则在"承认无法判定"上更强：100% vs 46.2%**。
  因为离线后端被明确编程为"判不了就标 uncertain"，而 LLM 倾向于给出结论。
- 按**判定单元**口径，离线后端（85.7%）**高于** DeepSeek（73.8%）：
  差异集中在「该不该下结论」的保守度上（旧口径重复计权，把这一差异抹平了）。

**这验证了本项目的分工设计：规则层的确定性事实 + LLM 的语义判断是互补的**，
而非简单替代关系。

> 一个诚实的补充：那 14 条"人工标 uncertain、LLM 判 false_positive"的差异中，
> 多数（如 axis 库的未使用信号、`pause_req` 未连接）**人工标注可能偏保守**，
> LLM 的判断反而更明确。也就是说，LLM 的真实优势被这份金标准**低估**了。

**上下文供给决定 LLM 表现（重要的工程经验）**

首轮只给 LLM 单行代码时，DeepSeek 一致率只有 **40.9%**，甚至低于离线后端。
补上"告警行附近的源码上下文 + 文件性质（是否行为仿真模型）+ 规则层语义标记"
之后提升到 **88.2%**。

**结论：接上大模型不等于变好，喂什么上下文才是决定性的。**
这也解释了本项目的架构为什么把"结构化事实提取"放在规则层 ——
规则层产出的 `tags`、文件性质、上下文窗口，正是 LLM 判准的前提。

**这次评测的最大价值在于推翻了我自己的一个设计假设。**

我原本让离线裁定器"基于规则先验直接下结论"，结果一致率只有 12.7% ——
它把 99 条本该豁免的告警全判成了"确认缺陷"。

复核数据后发现根本原因：**在成熟工程代码上，规则告警的绝大多数（79%）
并非需要修复的缺陷，而是需要豁免的合法写法**（行为仿真模型、块内临时变量、
有意位宽截断、仿真断言）。这意味着裁定层的核心能力不是"确认"而是**"豁免"**。

因此我把离线后端的姿态改为 **"能判的判，判不了的交出去"**：只对三类可明确
判定的情形下结论（行为仿真模型 / 块内临时变量 / 仿真调试代码），其余一律如实
标注 `uncertain`。一致率随之从 12.7% 提升到 **90.6%**。

剩余 11 条不一致全部是 R002 的"有意截断"（如 32 位 `gpio` 驱动 8 位 LED）——
离线后端无法区分"有意截断"与"意外截断"，如实标为 `uncertain`。
**这类需要设计意图判断的场景，正是真实大模型的价值所在**，也是本框架
预留 `--model / --base-url` 接口的意义。

> 这条经验对工程有直接价值：审查工具的判定输出必须区分
> 「确认缺陷 / 需豁免 / 无法判定」三态，而不是二值化的对错。
> 二值化会迫使工具在不具备判断力时做出错误断言，反而损害可信度。

### 5.4 工程可用性：豁免机制与 CI 落地

前两节解决"报得准不准"，这一节解决"工程师愿不愿意用"。

**豁免（waiver）机制**

真实项目必然存在"命中规则但设计者有意为之"的代码。若没有官方豁免通道，
工程师只能关掉整条规则（丢失检出能力）或在报告里人工忽略（噪音累积），
最终弃用工具 —— 这也是我判断"没有豁免机制就不算可用的 Lint 工具"的原因。

因此实现集中式、**强制带理由、可审计**的豁免配置 `.rtlsentinel.json`：

```json
{
  "waivers": [
    {"file": "spiflash.v", "rule": "R004", "reason": "行为仿真模型，非综合目标"},
    {"file": "picorv32.v", "rule": "R003", "lines": [1406, 1407],
     "reason": "块内顺序计算风格"}
  ]
}
```

设计原则是 **"豁免不隐藏"**：被豁免的告警仍出现在报告中，只是单独归入"已豁免"区
并注明理由；导出 SARIF 时以 `suppressions` 形式保留。若豁免能让问题凭空消失，
它就会从工程手段退化成藏问题的工具。

效果（真实语料 42 文件 / 15151 行）：

| 状态 | 告警数 | 风险分 | 健康分 |
| --- | --- | --- | --- |
| 未豁免 | 127 | 83.0 | 17.0 |
| 应用 14 条豁免规则 | **33** | **20.1** | **79.9** |

**风险分按代码规模归一化**：绝对加权和对大工程不公平 —— 15000 行里的 8 个 error
与 200 行里的 8 个 error 严重程度完全不同。基准设为「每千行 40 个加权缺陷 = 满风险」。

**CI 落地**：输出 SARIF 2.1.0，可被 GitHub Code Scanning 直接消费，审查结论以
行内批注出现在 PR 上；配合退出码约定（0 = 无 error / 1 = 有 error / 2 = 输入异常）
可直接做门禁。项目内含 `.github/ci-examples/rtl-sentinel.yml` 示例。

```bash
python -m rtl_sentinel.cli rtl/ -f sarif -o rtl-sentinel.sarif --no-llm
python -m rtl_sentinel.cli rtl/ --no-llm --min-severity error    # 门禁
```

### 5.5 第三方学术基准对标（LintLLM benchmark）

**动机**：前四节的数据都基于自建评测集，容易陷入"自己出题自己考"。
为避免这一点，我引入了 GLSVLSI 2025 论文 **LintLLM** 的**公开 benchmark**
（90 个 Verilog 模块 × 11 类注入缺陷，MIT 许可），人工转录其标注表后
写成自动化评估脚本 `bench/evaluate_lintllm.py`。

**上游论文的对比基线**（可参照）

| 工具 | 正确率 ↑ | 误报率 ↓ |
| --- | --- | --- |
| 商业 EDA | 64.44% | 27.78% |
| Verilator | 62.22% | 32.22% |
| o1-mini + LintLLM | 83.33% | 12.22% |

**本工具实测**

```
模块级检出率 : 23.3%  (21/90)        告警精确率 : 27.5%

Sensitivity List 44% │ Module Instances 38% │ Reserved words 33%
Operators 29% │ Port Type 25% │ Signal Usage 23% │ Bit Width Usage 21%
Race or Hazard 9% │ Syntax Structure 0% │ Logic Synthesis 0% │ Combinational 0%
```

**三条结论**

**① 定位差异被量化了。** 本工具在"可综合设计缺陷"上有效（敏感列表类 44%、
实例化类 38%），在"语法与声明类"缺陷上基本无覆盖（0%）。
这与 LintLLM 形成**互补而非竞争** —— 可形式化的缺陷（位宽算术、多驱动、CDC）
由确定性规则做零误报检查；语法/声明类缺陷（未声明信号、保留字误用）交给
大模型更划算。**我用实验验证了自己提出的架构判断，而不是停留在论断上。**

**② 发现并修复了一个真实盲区。** Bit Width Usage 初测只检出 14%，
根因是 R002 **对表达式一律跳过**。但 Verilog 的算术运算符不会自动扩展位宽 ——
`a + b` 的结果位宽是 max(width(a), width(b)) 而非 max+1，
因此 `reg [3:0] sum; assign sum = a + b;` 会静默丢失高位。这是经典 RTL 陷阱，
补上保守的表达式位宽推断后提升到 21%。**这个 bug 靠自建样例发现不了。**

**③ benchmark 本身存在方法论局限。** 它每个模块只标注"注入的那一处"缺陷，
未标注代码中自然存在的其他问题。因此任何检出额外问题的工具都会被计入"误报"
（Verilator 32.22% 的误报率有同样成因）。本工具 27.5% 的精确率被显著低估。

**本次对标带来的改进**：新增 **R011**（组合逻辑误用非阻塞赋值）、
**R012**（赋值运算符误用）、**R013**（实例化连接方式混用）三条规则 ——
分别对应 LintLLM 缺陷分类的 Combinational or Sequential、Operators、
Module Instances 三类，也都是 Verible 等工业工具覆盖的场景。
规则总数 10 → **13 条**。完整分析见 `docs/相关工作与资源调研.md`。

### 5.6 对照实验：该不该让大模型也参与「检测」？

前面的设计把 LLM 限制在"裁定"角色，检测交给规则引擎。但**这个分工是我的先验设定，
并没有被验证过**。所以我做了正面对照实验：让 DeepSeek **零提示工程**直接读源码
指出缺陷行（温度 0），与规则引擎在同一 benchmark 上比较。

**结果**

| 方案 | 模块级检出率 | 来源 |
| --- | --- | --- |
| 商业 EDA | 64.44% | 上游论文 |
| Verilator | 62.22% | 上游论文 |
| o1-mini + LintLLM（带逻辑树提示） | 83.33% | 上游论文 |
| **DeepSeek 直接检测（零提示工程）** | **72.2%** | 本次实测 |
| RTL-Sentinel 规则引擎 | 23.3% | 本次实测 |

**在"检出率"这个单指标上，规则引擎输了，我如实记录。**

但拆解后有两个更有价值的发现：

**① 两者的衰减方向相反**——这是本次实验最有价值的观察：

| 难度 | DeepSeek | 规则引擎 |
| --- | --- | --- |
| simple | **96.7%** | 23.3% |
| medium | 86.7% | 16.7% |
| complex | **33.3%** | **30.0%** |

代码越长，LLM 的注意力衰减越严重（96.7% → 33.3%）；
而规则引擎**不受代码长度影响**，在 complex 档几乎追平。
**这说明规则引擎的相对价值随代码规模上升。**

**② 工程属性不可替代**

| 维度 | DeepSeek 直接检测 | 规则引擎 |
| --- | --- | --- |
| 90 模块耗时 | 81.8 s | **18 ms（快 4500 倍）** |
| 成本 | 约 ¥0.1–0.3 | **0** |
| 可复现性 | 温度 0 也不保证逐字一致 | **完全确定** |
| 可否直接进 CI 门禁 | 否（自然语言，需人工复核） | **是** |

**修正后的结论**：不是"规则替代 LLM"，而是**两者分层** ——
LLM 适合探索式审查（高覆盖、需人工复核），规则引擎适合 CI 门禁
（零误报、毫秒级、可审计）。

**并且我把这个结论落地成了功能**：新增 `--llm-detect` 选项，
让大模型作为"检测通道"补充规则引擎的漏报：

```bash
python -m rtl_sentinel.cli rtl/ --llm-detect -f html -o report.html
```

三条硬约束保证不破坏可复现性：① 输出标记 `needs_review`，报告中显示为
「待复核 · LLM 线索」；② severity 强制为 info；③ **不计入风险分**，不影响 CI 门禁。

实测（受控样例集（当时 9 文件，现为 12 文件））：规则引擎 32 条 → 启用后 63 条（补充 31 条线索），
**风险分保持 100.0 不变**。补充线索质量可用 —— 例如它准确指出
`fsm_buggy.v L23`"else-if 链无终结 else，S_DONE 时 nstate 无赋值，推断 latch"，与规则 R001 结论一致。

> 这个实验的价值不在于得出一个漂亮的数字，而在于
> **我用实验检验了自己的设计假设，发现它部分不成立，据此修正结论，
> 并把它转化成了一个有明确边界的新功能**。

## 六、工程闭环案例：缺陷的发现与修复

这部分比指标本身更能说明工程能力。以下每个问题都走完了
**"现象 → 定位根因 → 修复 → 回归验证"** 的完整闭环，且回归后受控评测集始终满分（现为 24/24）。

### 6.1 行号精度（三轮迭代）

审查工具如果行号报错，工程师根本无法定位，工具价值直接归零。踩过三个坑：

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 注释剥离后全部行号错位 | 直接删除注释会压缩文本 | 注释替换为**等长空格**并保留换行符 |
| 跨行语句行号偏小 1~2 行 | 按语句起始行计行号，而赋值可能在下一行 | 改为按**赋值目标出现位置**换算行号 |
| 模块体内声明行号偏小 1 行 | 语句起点落在上一行的换行符上 | 跳过前导空白后再换算行号 |

### 6.2 `for` 循环头被误判为时序赋值

```verilog
always @(posedge clk) begin
    for (i = 0; i < 4; i = i + 1) begin   // 循环控制 i = 0 被误报为阻塞赋值
        acc <= acc + i;
    end
end
```

**根因**：语句按 `;` 切分，而 `for` 循环头本身含两个分号。
**修复**：预扫描所有循环头的偏移区间，其内的分号不作为语句边界、
其内的赋值匹配被跳过。回归后该用例告警归零。

### 6.3 干净基线误报：两次掩码缺一不可

"未使用信号"（R008）的误报最隐蔽，需要**两次掩码**同时成立：

```
只抹赋值左侧  →  声明语句 reg [1:0] dbg_state; 里的名字被算作"被读取" → 漏报
只抹声明      →  shreg <= {.., shreg[7:1]} 的自引用被算作"只写不读"  → 误报
两次都做      →  正确
```

同时还要保留声明式初始化 `wire wr_ok = wr_en && !full;` 的右式，
否则 `wr_en` / `full` 会被反向误报 —— 这正是首轮真实代码验证中 Precision
只有 94.4% 的原因。

### 6.4 `<=` 双重语义（真实代码暴露的关键缺陷）

```verilog
if (long_counter_reg <= word_cnt) begin   // 这是"小于等于"比较
    ...
end
```

`<=` 在 Verilog 中**双重语义**：既是非阻塞赋值，又是"小于等于"运算符。
原实现把它误判为对 `long_counter_reg` 赋值，污染了信号驱动集合，
间接制造出大量假的多驱动告警。

**修复**：用**括号深度**消解歧义 —— 预计算每个位置的括号嵌套深度，
深度为 0 说明 `<=` 在语句顶层（赋值），深度 > 0 说明在括号内（比较）。

> **这是本项目最有价值的一次发现**：自造样例时我天然避开了易混淆写法，
> 只有真实开源代码才能暴露这种语义盲区。修复后 R004 从 215 条直降到 8 条。

### 6.5 累计效果

| 阶段 | 受控评测集 | 真实语料 error 级 |
| --- | --- | --- |
| 初版 | 21/21 | 397 |
| 跨文件模块索引 + 参数化/条件编译识别 | 21/21 | 62 |
| `<=` 双语义修复 + 位分段驱动识别 | 21/21 | 25 |
| LHS 位选 / 数组下标区分 | **21/21** | **26**（告警总数从 149 降到 126） |
| 调研补充 3 条规则 + 表达式位宽推断 | **21/21** | **27**（告警总数 127） |

## 七、已知局限（主动披露）

1. **解析覆盖度**：支持 Verilog-2001/2005 常用子集；不支持 UDP 原语、宏展开、
   完整 SystemVerilog 类与断言语法。`generate` 目前仅用于抑制表观多驱动，
   未做分支语义展开，因此参数化设计下的跨模块检查仍不完整。
2. **跨模块 CDC 未覆盖**：R006 仅检测同模块内跨时钟域；且判定"已同步"依赖
   `_sync` / `_gray` 命名约定，属启发式手段而非结构分析。
3. **位宽推断深度**：R002 基于声明位宽与字面量，不做完整的表达式位宽传播。
4. **R009 的边界**：对带参数覆写的实例不做判断（无法确定覆写后的端口位宽）。
5. **R003 的风格误判**：对"用阻塞赋值做块内顺序计算"的编码风格（如 picorv32）
   会命中，属设计风格差异而非真实缺陷，已降为 warning 并在消息中说明。
6. **真实语料仍有残余告警**：25 条 error 中有 8 条来自 SPI Flash 行为仿真模型，
   属"告警本身正确、但对象并非综合目标代码"。
7. **离线裁定器**：用规则化先验模拟语义判断，不等价于真实 LLM 的语义理解能力。

## 八、复试 / 保研面试问答准备

**Q1：为什么不做成"直接把代码丢给大模型让它审"？**
> 我实测并分析过这条路。大模型在两类任务上不可靠：一是位宽算术，
> 因为 tokenization 会破坏数字的位级语义，它无法稳定区分 `4'hF` 与 `8'hFF`；
> 二是数据流追踪，跨多个 always 块追踪一个信号的驱动源容易漏。
> 更关键的是不可复现——同一个文件两次审查结果可能不同，这在工程上无法接受。
> 所以我把"发现问题"交给确定性规则，"解释问题"交给大模型。

**Q2：为什么不用 SpyGlass、Verilator 这些现成工具？**
> 两个原因。一是商业工具 license 昂贵，个人和教学场景不可得；
> 二是它们只告诉你"第几行有问题"，不解释根因、不给修复补丁，
> 而后者对初学者和快速迭代恰恰是最有价值的。
> 另外我这个实现零第三方依赖，任何环境一条命令就能跑，这在教学和演示场景很有意义。
> 补充：我并不是完全不用这些工具 —— 我还用 **Verilator 做了交叉验证**：
> 让它独立复核我的缺陷样例，确认了多驱动、阻塞/非阻塞混用等判定，并把这一步
> 接进了 **CI 门禁**。所以定位不是重复造轮子，而是与其**互补** —— Verilator 覆盖
> 语法/结构，本工具覆盖需要判断设计意图的设计缺陷。

**Q3：100% 的准确率，怎么保证不是过拟合？**
> 首先我明确它来自自建受控样例集，用来验证规则逻辑的正确性和零误报特性，
> **不代表真实工程代码上的表现**，这一点我在 README 里主动写明了。
> 其次防过拟合的手段是：缺陷标注是**先写代码、再人工标注**，
> 而不是反向适配规则输出；两个干净基线专门用于度量误报率，
> 一旦规则写宽松了，基线就会报警，指标会立刻掉下来。
> 这一步已经完成：在 3 个真实开源仓库（42 文件 / 15151 行）上做了泛化验证，并用 Verilator 做了外部交叉验证。

**Q4：解析器是你自己写的？为什么不用 ANTLR？**
> 自己写的。理由有三：一是 Verilog 完整语法（IEEE 1364）是个大工程，
> 而规则引擎真正需要的只有四类静态事实——声明、过程块、驱动关系、控制结构特征；
> 二是引入 ANTLR 会带来 Java 或 Python 运行时的第三方依赖，
> 破坏"任意环境可跑"这个对教学演示很重要的特性；
> 三是我的解析管线对残缺代码不抛异常，适合前端实时审查场景。
> 代价我也清楚：放弃了完整语法树能力，`generate` 展开目前不支持。

**Q5：这个项目里最难的技术问题是什么？**
> 是**行号精度**。审查工具如果行号报错，工程师就无法定位，工具价值直接归零。
> 我踩过三个坑：一是注释剥离时如果直接删掉注释，后续所有行号都会错位，
> 改为替换成等长空格并保留换行；二是跨行语句——`case` 项里的赋值语句
> 起始行和赋值行差一到两行，改为按赋值目标出现的位置换算行号；
> 三是 `for` 循环头里的分号被当成语句边界，导致循环控制被误判为时序赋值，
> 通过预先扫描循环头偏移区间解决。每修一个都跑了回归测试。

**Q6：大模型在这个系统里具体起什么作用？怎么衡量它的价值？**
> 它做三件事：判定这条规则告警是真缺陷还是误报、归纳根因、生成修复补丁和验证方法。
> 衡量的方式是我把 LLM 的输出设计成结构化的 `{verdict, reason, patch}`，
> 其中 `verdict` 可以和人工标注直接比对，算出一致率。
> 另外系统做了可插拔设计：离线时用启发式裁定器保证功能不缺失，
> 在线时接任意 OpenAI 兼容后端（包括本地 vLLM / Ollama），
> 这样同一套评测集可以横向对比不同模型的效果。

**Q7：如果继续做，下一步是什么？**
> 按优先级排：第一，在开源 RTL 仓库上做增量验证，度量真实误报率——
> 这是把"受控验证"变成"真实可信"的关键一步；
> 第二，建立 LLM 裁定与人工标注的一致性评测，量化语义推理层的准确率增益；
> 第三，支持 `generate` 与宏展开；
> 第四，和 Yosys 联动，用综合报告交叉验证审查结论；
> 第五，做成 VS Code 插件，实现保存即审查。

**Q8：这个项目跟你学的集成电路专业有什么关系？**
> 13 条规则本身全部来自数字设计的真实规范：latches 推断、跨时钟域同步、
> 阻塞与非阻塞赋值的区别、综合不可用结构——这些正是《数字集成电路设计》
> 和《Verilog HDL》课程里的核心知识点，只是我把它们从"人脑检查"
> 变成了"工具自动检查"。同时 Verilog 样例是我自己写的，
> 包括 UART 发送器、同步 FIFO、状态机、跨时钟域模块，
> 干净基线版本是可以直接综合的工业写法。

**Q9：位宽检查具体怎么实现的？**
> 分三种情况。右侧是单一标识符时，比较两侧声明位宽；
> 右侧是显式位宽字面量（如 `8'hFF`）时，取字面量位宽比较；
> 右侧是十进制常量时，按数值所需的最小位宽推断——比如 20 需要 5 位，
> 赋给 4 位寄存器就会报截断，这是商用工具也容易漏的一类。
> 右侧是复合表达式时我选择跳过，因为没做完整的位宽传播，
> 宁可漏报也不误报——审查工具最大的敌人是噪音。

**Q10：风险评分是怎么设计的？**
> 每条告警的权重 = 严重度权重 × 置信度。严重度分 error/warning/info
> 三档，权重分别是 10/4/1；置信度是规则自身对判断把握程度的主观刻画，
> 比如多驱动是确定性事实给 1.0，跨时钟域需要结合设计意图给 0.8。
> 所有未被 LLM 判为误报的告警权重求和，饱和映射到 0-100 就是风险分，
> 取 100 减去它得到健康分。这个设计的目的是让"一行错误"和"十个提示"
> 不混淆，便于 CI 门禁设阈值。

**Q11：你提到在真实开源代码上做了验证，具体发现了什么？**
> 这一步比做样例集重要得多。我拉了三个真实仓库（picorv32 的 RISC-V 软核、
> 以及两个工业风格的 UART 和 AXI-Stream 库），共 42 个文件 15000 多行。
> 首轮跑出 491 条告警、其中 397 条 error —— 成熟开源项目不可能有 397 个致命缺陷，
> 这个数量级本身就说明我的规则有系统性误报。
>
> 逐条人工复核后定位出 7 类根因，最重要的两条是：
> 一、实例化时我没有判断端口方向，把 `SB_SPRAM256KA` 的 `.CHIPSELECT(cs_0)`
> 这种输入连接也当成了驱动源，单这一项就产生 200 多条假多驱动 ——
> 这直接促成了我加入**跨文件模块索引**；
> 二、更关键的是发现了一个解析器语义盲区：`if (a <= b)` 里的"小于等于"
> 被误认成了非阻塞赋值，因为 `<=` 在 Verilog 里是双重语义。
> 我最后用**括号深度**来区分：语句顶层是赋值，括号内是比较。
>
> 修完之后 error 从 397 降到 27，降了 93%，而受控评测集始终满分没有退化（现为 24/24）。
> 这件事让我真正理解了：**自造样例只能证明逻辑写对了，只有真实代码能暴露语义盲区**。

**Q12：你怎么知道大模型在这个系统里真的有价值？**
> 我做了量化评测。规则层负责发现问题、推理层负责裁定真伪，但后者的能力之前
> 从未被量化。所以我人工复核了真实语料上的告警，构造了一份裁定金标准
> （43 个 (文件, 规则) 组合 / 126 条告警），标准是"该告警是否指向一个需要
> 修改的真实问题"。
>
> 结果我第一次的实现一致率只有 **12.7%** —— 它把 99 条本该豁免的告警全判成了
> 确认缺陷。复核后发现根本原因：**在成熟工程代码上，规则告警的 79% 并不需要
> 修复，而是需要豁免的合法写法**。这意味着裁定层的核心能力是"豁免"而非"确认"。
>
> 于是我把姿态改成 **"能判的判，判不了的交出去"**：只对三类可明确判定的情形
> 下结论（行为仿真模型、块内临时变量阻塞赋值、仿真调试代码），其余一律如实标
> `uncertain`。一致率随之从 12.7% 提升到 **90.6%**。
>
> 剩下 11 条不一致全部是"有意位宽截断"（如 32 位 gpio 驱动 8 位 LED）——
> 这类必须判断设计意图，正是真实大模型的价值所在。框架里已经预留了
> `--model / --base-url` 接口，接入后一行命令就能复现同一份评测、横向对比模型。
>
> **后来我接上 DeepSeek 真的跑了一遍，结果比预想的有意思**：
> 总一致率和离线后端差不多（88.2% vs 90.6%），但拆开看差异很清楚 ——
> 在"判断某段代码是设计者有意为之还是笔误"这个语义任务上，
> LLM 判对了 **100/101 条（99%）**，明显强于离线硬规则的 88.1%；
> 反倒是"承认自己无法判定"这件事硬规则更靠谱（100% vs 46.2%），
> 因为离线后端被明确编程为"判不了就交出去"，而 LLM 倾向于给结论。
>
> 这恰好说明两者是互补的：规则负责给出确定性事实，LLM 负责语义判断。
> 还有一个教训 —— 我第一次给 LLM 的上下文只有一行代码，一致率只有 40.9%，
> 比离线后端还差；补上源码上下文、文件性质、规则层标记之后才到 88.2%。
> **接上大模型不等于变好，喂什么上下文才是决定性的。**
>
> 这件事给我的启发是：**审查工具的判定输出必须区分「确认缺陷 / 需豁免 / 无法判定」
> 三态**。二值化会迫使工具在不具备判断力时做出错误断言，反而损害可信度。

**Q13：为什么要做豁免机制？**
> 因为我在真实代码上验证时就发现：规则告警的 **79% 是"需要豁免"而不是"需要修复"**。
> 如果没有官方豁免通道，用的人只有两个选择 —— 关掉整条规则，或每次在报告里
> 人工忽略。前者丢失检出能力，后者噪音累积，最后一定是弃用工具。
>
> 所以我做了集中式豁免配置，并且有一条硬约束：**每条豁免必须写理由**，
> 否则配置不生效（代码里直接过滤掉没有 reason 的条目）。
> 另外坚持**豁免不隐藏** —— 被豁免的告警仍然出现在报告里，只是单独标记，
> 导出 SARIF 时以 `suppressions` 形式保留。因为如果豁免能让问题凭空消失，
> 它就从工程手段退化成藏问题的工具了。
>
> 配套还改了风险分算法：原来是绝对加权和，导致 15000 行代码里有 8 个 error
> 也判 0 分、而 200 行里 8 个 error 也是 0 分，完全没有区分度。
> 改成按代码规模归一化（每千行加权缺陷数）后，真实语料应用 14 条豁免规则，
> 健康分从 17.0 升到 **79.9**，这个分数才有工程意义。

**Q14：你怎么证明你的工具比大模型做得好？**
> 我没有这么说，反而做了实验去证明两条路线各有疆域。
>
> 我找到了 GLSVLSI 2025 的一篇论文 LintLLM，它让大模型直接做 Verilog 缺陷检测，
> 靠"逻辑树提示"把正确率做到 83.33%，比商业 EDA 工具高 19 个百分点。
> 我把它的公开 benchmark（90 个模块、11 类注入缺陷）拉下来跑我的工具，
> 结果是模块级检出率 23.3%。
>
> 但这个数字不能简单读成"输给了大模型"。按缺陷类型拆开看就清楚了：
> 敏感列表类我检出 44%、实例化类 38%，而语法结构类、逻辑综合类我是 0%。
> 也就是说，我在**可综合设计缺陷**上有效，在**语法与声明类**缺陷上基本没覆盖。
>
> 这恰好验证了我的架构判断：可形式化的缺陷（位宽算术、多驱动、跨时钟域）
> 本质是符号计算，交给确定性规则能做到零误报、可复现；而语法和声明类缺陷
> 交给大模型更划算。所以我做的是"规则负责发现、LLM 负责裁定"的分工，
> 不是要替代大模型。
>
> 这次对标还帮我抓出一个真实盲区：位宽类我只检出 14%，查下来是我的 R002
> 跳过了所有表达式，但 Verilog 的加法**不会自动扩位** ——
> `reg[3:0] sum; assign sum = a + b;` 会丢进位。补上表达式位宽推断后提升到 21%。
> 这个 bug 靠自建样例永远发现不了，只有拿到别人的题才能暴露。
>
> 另外我也发现这个 benchmark 有个方法论局限：它每个模块只标注注入的那一处缺陷，
> 没标注代码里自然存在的其他问题，所以任何检出额外问题的工具都会被算成"误报"
> —— Verilator 在那个 benchmark 上有 32% 误报率，也是同样成因。

**Q15：你为什么不让大模型直接做检测？**
> 我一开始就是这么分工的 —— 规则负责发现、LLM 负责裁定。但我没有停在论断上，
> 而是做了对照实验去检验它。
>
> 我让 DeepSeek 零提示工程直接读源码找缺陷，和我的规则引擎在同一套 benchmark 上比。
> 结果是 **72.2% vs 23.3% —— 在检出率这个指标上我输了**。
>
> 但这个结果不能简单接受，得拆开看。有两个发现：
>
> 一是**衰减方向相反**：DeepSeek 在简单模块上 96.7%，到复杂模块只剩 33.3%；
> 而我的规则引擎不受代码长度影响，复杂档反而是 30%，基本追平。
> 说明规则引擎的相对价值随代码规模上升。
>
> 二是**工程属性完全不同**：90 个模块 DeepSeek 要 82 秒，我的规则引擎 18 毫秒，
> 快 4500 倍；而且规则的输出完全确定、结构化、能直接做 CI 门禁，
> LLM 的输出是自然语言、必须人工复核，也不保证逐字复现。
>
> 所以我把结论修正成：不是"规则替代 LLM"，而是**两者分层** ——
> LLM 适合探索式审查，规则适合门禁。这个修正我如实写进文档了。
>
> 我觉得这个过程本身比结论重要：**先验的设计假设要用实验去检验，
> 发现它部分不成立就修正它**，而不是找证据证明自己一开始就是对的。

## 十一、独立标注（盲标）流程

金标准目前是“自产自评”，这是已知的方法论短板。要把它变成可信数字，需要**没有
看过现有结论**的独立方重新标注。两种做法：

- **人工标注（首选）** —— 找一位数字设计方向的同学，约 1 小时。可信度最高。
- **跨模型标注（退而求其次）** —— 用**另一个厂商**的模型（如 GPT / Claude / Gemini /
  Qwen）做标注者。注意：这优于自产自评，但**不等于人工金标准**，对外表述须如实写明
  标注者身份；**不要用 DeepSeek** —— 本系统的 LLM 裁定后端就是 DeepSeek，同族模型会
  共享偏好，独立性弱。

流程：

1. 生成盲标清单（不含任何现有判定，因此是“盲”的）。**推荐二元协议** ——
   三态量表里“要不要弃权”的自由度极大，实测让跨标注者一致率在 47.6%~95.2%
   之间摆动，**弃权是分歧之源**；二元协议把问题改成“改代码 / 标豁免”并附 4 条校准样例：

   ```bash

   # 推荐：二元协议 + 文件级事实（消除信息不对称）
   python bench/prepare_blind_labels.py --protocol binary --file-facts
   python bench/prepare_blind_labels.py --protocol binary --file-facts --limit 30 --seed 0
   python bench/prepare_blind_labels.py --protocol binary          # 不加文件事实（对照）
   python bench/prepare_blind_labels.py                           # 三态（旧口径，供对照）
   ```

   产出：`out/blind_labels_binary_facts.md`（给人阅读）、`out/blind_labels_binary_facts.csv`
   （给人填写）、`out/label_prompt_binary_facts.md`（给 AI 的完整提示词，整段复制即可）。
   其中 `--file-facts` 会给每条附一行**文件级事实**（文件行数 / 是否含 `#N` 延时 /
   是否含 task 定义）—— 标注方只能看到告警附近几行，实测中这一信息不对称造成了
   约一半的标注分歧（例如把行为级文件误判为需要修改的缺陷）。评测端会**额外**给出
   “选择性预测”指标（弃权率 / 不弃权时的准确率 / 对「需改代码」的召回），避免把
   “弃权”与“判错”混为一谈。
2. 交给标注方。**不要**让其看到 `golden_adjudication.json`；取值定义写在清单头部
   （二元协议为 `change` / `waive` / `abstain`；三态协议为 `confirmed` /
   `false_positive` / `uncertain`）。
   - 人工：填 CSV 的 `verdict` / `reason` 两列。
   - AI：把 `out/label_prompt.md` 整段粘贴进去，把返回的 CSV（`id,verdict,reason`）
     存成 `out/ai_labels.csv`。
3. 合并回金标准并复评：

   ```bash

   python bench/merge_blind_labels.py out/blind_labels.csv --rater "同学 A"
   python bench/merge_blind_labels.py out/ai_labels.csv --rater "GPT-5"   # AI 路径
   python bench/evaluate_adjudication.py
   ```

   评测会单列“独立人工标注子集”的一致率 —— **那才是对外可引用的数字**。
4. `git commit` 记录本次标注，便于追溯来源。

> 判据提示：这些告警来自成熟开源代码，多数并非缺陷。如实判断即可，不必迎合工具。

### 附：标注者一致性实验（2026-10-10 实测）

同一批 42 个判定单元，交给不同标注方（不同模型 / 不同提示词），结果如下：

| 标注方（模型 + 提示词） | 与工具（离线后端）一致率 | 标注内部 verdict 分布 |
| --- | --- | --- |
| 自评金标准（循环，仅参考） | 85.7% | false_positive 27 / uncertain 15 |
| 豆包 2.1 **lite** + 带先验提示词 | 50.0% | false_positive 40 / confirmed 2 / uncertain 0 |
| 豆包 2.1 + 中性提示词 | 45.2% | false_positive 20 / confirmed 18 / uncertain 4 |
| GLM 5.3 + 中性提示词 | 50.0% | **false_positive 42** / confirmed 0 / uncertain 0 |

标注方**之间**的一致率：豆包 lite·带先验 vs GLM = **95.2%**；豆包 lite·带先验 vs 豆包2.1 = **47.6%**；
豆包2.1 vs GLM = **47.6%**。

其中最干净的一组对照是 **豆包 2.1 与 GLM 5.3（同一版中性提示词、不同模型）**：
两者彼此仅 **47.6%** 一致 —— 说明**模型身份本身就是主要方差来源**。
（豆包 lite 与豆包 2.1 之间 2 条 vs 18 条 confirmed 的差异，同时混了“模型版本”与
“提示词”两个变量，**不能单独归因于提示词**。）
豆包2.1 vs GLM = **47.6%**。

**结论**：“裁定一致率”不是工具的属性，而是“工具 × 标注者”配对的属性 —— 同一批题目
仅因换了标注者就在 45%~96% 之间摆动；分歧几乎全部集中在“要不要弃权”上。
因此本项目**不主张单一一致率数字**，改为三条：① 用二元协议压缩弃权自由度；
② 报告选择性预测指标（弃权率与不弃权时准确率分开）；③ 对外如实标注金标准的
来源、规模与协议 —— 这也是本作品最诚实、也经得起追问的一个方法论结论。

### 附：工具侧的一个关键事实（同日实测）

把离线裁定器在同一批 42 个判定单元上的输出拆开看：

- 弃权（uncertain）：**21/42 = 50%**
- 作出裁定：21/42，且**全部是 false_positive** —— 一个 `confirmed` 都没有

这解释了上面的数字：“与工具一致率”实际上是在衡量“标注方是否也不说 confirmed”。
与“全判 false_positive”的标注集在非弃权时达到 100% 一致，是**基准率效应**，
不能读成“工具不弃权时 100% 准确”。

为什么一个 confirmed 都没有：`llm.py` 中只有 `_HARD_FACTS = {R004, R009}` 会判
confirmed，而本语料里仅有的 R004 出现在 `spiflash.v` —— 那是**行为级仿真模型**，
在更早的“仿真模型”分支就被判为 false_positive 了。因此 confirmed 路径在本语料上
从未触发。

**对定位的启示（重要）**：本工具语义推理层在真实代码上的价值，应表述为
**“减少误报（把不该改的判为豁免）”**，而不是“发现真实缺陷” —— 至少在当前的
规则集与语料上是如此。这也是后续最该补的能力。

（另一处细节：豆包 2.1 与工具在非弃权单元上的 6 条分歧**全部集中在 `spiflash.v`**。
标注方只拿到告警附近 8 行上下文，看不到“该文件是行为级仿真模型”这一**文件级**
事实，于是判成了 confirmed。属上下文供给差异，而非工具漏报。）

把同一比较换到**系统的真实后端**（DeepSeek）上，结论不变而且更明确：
DeepSeek 在这 42 个单元上弃权 8 个（19%），而**它的 34 条确定性裁定全部是
`false_positive`**（可由“它与‘全判 FP’的标注集在非弃权时 100% 一致”反推得到）。

也就是说：本系统的裁定层在真实代码上**几乎不确认缺陷** —— 改进前是 **0 条**，本轮
改进后也只有 **2 条**（`axis_ll_bridge.v` 的 R003）。因此“与工具一致率”几乎完全由
“标注方也说 false_positive 的比例”决定：全判 FP 的标注集一致率 79%~81%，而找出
18 条缺陷的标注集只有 **47.6%**。

**本轮已据此改进**：把“**非块内临时量的 R003**”从 `uncertain` 升级为 `confirmed`。
判据本身是确定的（阻塞赋值 → 仿真与综合的更新时刻不一致），且三方证据一致：上游曾
**真实修复过该模式**（见第十二节回溯案例）、两个独立标注模型在二元协议下**唯一共同判
`change`** 的条目正是它。语料上因此出现那 2 条 confirmed；而**自产金标准在这条上标的
却是 `false_positive`** —— 恰好说明自产金标准本身也会错。

**也要澄清：这不等于“工具不会判 confirmed”。** 同一个离线裁定器在**植入缺陷的样例集**
（`samples/`，35 条告警）上给出 **9 条 confirmed**；成熟开源语料上则是 89 条
false_positive、36 条 uncertain、**2 条 confirmed**。也就是：

- `confirmed` 路径是通的，只是在**成熟代码**上很少触发（需 R004/R009 这类硬事实，
  或本轮新增的“非块内临时量的 R003”；而成熟工程里这类问题大多已被作者解决）；
- 所以 `change 召回 = 0%` 在很大程度上是**语料的属性，而不是工具的缺陷** —— 要测
  “发现缺陷”的能力，就该在含真缺陷的语料上测，那正是受控样例集（`bench/evaluate.py`）。

### 附：二元协议的效果（同日实测）

把同一对标注方（豆包 2.1 lite 与 GLM 5.3）换用**二元协议**（change / waive）重标一遍：

- 标注方**彼此一致率从 47.6%（三态·中性提示词）提升到 83.3%**，且两者都是 0 次弃权。
  这验证了“弃权自由度是分歧之源”：把“要不要弃权”这一维去掉后，分歧回到“改不改”本身。
- 标注方分布：豆包 lite 判 change **8 条**；GLM 判 change **1 条**（是豆包那 8 条之一）。

但工具的**方向性能力**也随之暴露得更清楚：**`change` 召回 = 0%** ——
离线后端 **0/8**、真实后端 **0/8**（对 GLM 的 0/1 同样为 0）。也就是：
独立标注方认为“需要改代码”的条目，工具**一条都没有确认**。

把那 8 条拆开看：

- **4 条工具弃权**：#9 / #17 / #34（R010 实例端口未连接）、#18（R003 阻塞赋值误用）
- **4 条工具判豁免**：#35–#38，全部在 `spiflash.v`（行为级仿真模型）—— 工具是有
  文件级依据的，这 4 条更像标注方缺少上下文

**所以真正值得做的不是“逼工具多判 confirmed”**：那 8 条里 4 条是行为级仿真模型，
工具有文件级依据判豁免；另 4 条连另一个独立标注方 GLM 也判 waive —— 强行 confirmed
只会制造误报。更该做的是**给标注方补齐文件级事实**（见下），让可靠性测量本身更公平。

### 附：文件级事实实验（否证结果）

**假设**：剩余分歧来自“标注方只能看告警附近 8 行”的信息不对称（例如把行为级仿真
模型误判为需修改的缺陷）。**做法**：给每条附一行**中性的文件级事实**（文件行数 /
是否含 `#N` 延时 / 是否含 task 定义），重跑同一对模型。

**结果**：两个模型的决策**逐条 100% 不变**（42/42），彼此一致率仍是 **83.3%**。
但 GLM 的理由明确引用了文件事实（“含延时与 task（文件事实）证实为行为级仿真模型”），
说明信息确实被读到了 —— 只是**没有改变判断标准**。

所以该假设**被否证**。剩余分歧的真实来源是**审查范围的判断标准不同**：

- 豆包：仿真模型里的 latch 推断 / 阻塞赋值 / 悬空端口**也算要改**（因为仿真行为会出错）；
- GLM 与工具：非综合目标代码 → **豁免**。

两种立场都合理，但提示词从未定义按哪一个。为此二元协议提示词新增 **【裁定范围】**
一节：明确以“可综合的 RTL 设计代码”为范围，行为级仿真模型整体豁免，但“仿真与综合
行为的一致性”仍在范围内。

> 诚实声明：这是**先看到分歧、再定义范围**，存在循环论证风险。因此该版本的一致率
> 不能与前一版直接比较，只能解读为“在明确范围下的一致性”。

这一步也顺带说明了整章的方法论：**裁定一致率只有在先定义清楚“在什么范围内裁、
按什么标准裁”之后才有意义** —— 否则不同标注方只是在按各自默认的范围作答。

## 十二、真实 bug 回溯验证

受控样例集是“我们植入的缺陷”，真实语料是成熟代码（没有真缺陷可确认）—— 两者都
回答不了“它到底能不能发现问题”。为此引入第三类证据：**开源项目真实修过的 bug**。

做法：把上游的 bug 修复提交拿来做回溯，用**修复前**的版本跑本工具，看能否指出作者
当年修掉的那个问题；再用**修复后**的版本确认告警消失。复现：`python bench/evaluate_backtest.py`。

| 案例（上游 commit） | 缺陷 | 期望规则 | 修复前 | 修复后 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `axis_pipeline_fifo`「Fix assignment type」 | `always @(posedge clk)` 的 `if(rst)` 分支内对寄存器数组用**阻塞赋值**清零 | R003 | **命中 L161/L162** | 未命中 | **PASS** |
| `axis_ram_switch`「Fix spurious multi-driven net」 | `int_cmd_tid` 的 `+:` 位选拼接在 `S_ID_WIDTH=0` 时退化为重叠区间 → 多驱动 | R004 | 未命中 | 未命中 | known_miss |

**第一个案例顺带查出并修复了工具自身的一处真缺陷**：回溯时 R003 没报，根因是
`axis_tvalid_reg` 的声明落在 `if (LENGTH > 0)` 生成块区内、被解析器的区间屏蔽，符号表里
查不到该信号，而 R003 当时有 `if not mod.signal(a.lhs): continue` —— **静默跳过**。

修法两处（都朝向“宁可多报、不可静默漏报”）：

1. R003 不再因“符号表查不到”而跳过（只跳过明确是 `parameter` / `localparam` 的目标）；
2. `_is_block_local` 在符号表查不到该信号时**不再发放块内临时量豁免** —— 无法证明就不豁免，
   避免把真缺陷误豁免掉。

**第二个案例是已披露的能力边界**：该缺陷只在参数 `S_ID_WIDTH = 0` 时成立，而本工具不做
参数化展开（`generate` 分支与参数覆写均不展开），因此在源码默认参数下不报。它被登记为
`known_miss` 如实计入边界，而不是悄悄丢掉。

> 附注：`bench/corpus/` 抓取的是各仓库**当前 master**，因此其中已是修复后的代码 ——
> 这也解释了为什么修 R003 后语料告警数仍是 127：那处修复发生在 2021 年，早已进入 master。

**顺带做了一次“扫射”**：把 verilog-axis 与 picorv32 的修复类提交（含 `.v` 改动）共
**19 个**逐一做了同样的修复前/后对照，只有 **1 个**（上表案例 A）落在本工具的规则射程内
（约 **5%**）。其余 18 个都是**逻辑类** bug（off-by-one、backpressure、索引越界、变量
作用域等），本工具的规则集根本不建模这类问题 —— 这与 LintLLM benchmark 上“模块级检出
23.3%、语法/声明类 0%”一致：**本工具定位在“设计模式类缺陷”，不覆盖逻辑正确性**。
