# RTL-Sentinel 架构设计

## 1. 核心设计判断：双引擎分工

本项目的全部架构都服务于一个判断：

> **代码审查中的"发现问题"和"解释问题"是两类不同性质的任务，必须由不同机制承担。**

- **发现问题** = 符号计算。判断 `reg [3:0] x; x <= 8'hFF;` 会截断，本质是在做
  位宽算术，需要精确、可复现、可写测试用例。LLM 由于 tokenization 会破坏数字的
  位级语义（把 `4'hF` 和 `8'hFF` 都感知为"像 0xFF 的数值"），在这类任务上会
  系统性出错且不可复现。
- **解释问题** = 语义理解。归纳根因、给出补丁、建议验证方法，这是 LLM 的强项。

因此系统被切成两层，且**接口方向被严格限制为单向**：

```
规则引擎 ──(告警 + 源码片段)──▶ LLM ──(裁定 + 根因 + 补丁)──▶ 报告
       ◀── 不允许 ──
```

LLM 无法凭空产生新告警，这是抑制幻觉的结构性保证，而不是靠提示词祈祷。

## 2. 分层结构

| 层 | 模块 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| 解析层 | `parser.py` | RTL 源码文本 | `Module{signals, always_blocks, assigns, instances}` | 不抛异常；行号与原文件严格一致 |
| 索引层 | `index.py` | 全工程文件列表 | `ModuleIndex{模块名 → 端口表}` | 未定义模块保守返回 None，不猜测 |
| 规则层 | `rules.py` | `Module` + `ModuleIndex` | `List[Finding]` | 纯函数；零随机；零网络 |
| 调度层 | `engine.py` | 文件/目录 | `ReviewResult{findings, risk_score}` | 单规则异常隔离；先建索引后审查 |
| 推理层 | `llm.py` | `List[Finding]` + 源码 | 补充 `verdict/reason/patch` | 禁止新增告警；三态裁定 |
| 豁免层 | `waiver.py` | `List[Finding]` + 配置文件 | 标记 `waived` | 强制带理由；豁免不隐藏 |
| 报告层 | `report.py` | `ReviewResult` | Text/MD/HTML/JSON/SARIF | 无状态 |

**为什么索引层必须独立且先于规则层**：真实工程是多文件互连的，规则层判断
"某信号是否被多驱动"时必须知道实例端口的**方向**，判断"端口位宽是否匹配"时
必须知道被实例化模块的**端口位宽**。这些信息都不在当前文件里。
若不做全局索引，实例的所有连接只能被保守忽略（大量漏报）或全当驱动源
（大量误报，实测 200+ 条）。

## 3. 解析层设计

### 3.1 为什么不用 ANTLR / Yacc

完整 Verilog 语法（IEEE 1364-2005）是个大工程，且引入第三方依赖会破坏
"零依赖、任意环境可跑"这一对教学与演示至关重要的特性。更关键的是：
**规则引擎需要的不是完整语法树，而是四类静态事实**：

1. 信号声明（方向 / 存储类 / 位宽）
2. 过程块的时钟域、敏感列表、块内赋值
3. 连续赋值与实例化驱动的连接关系
4. 控制结构特征（是否有 else / default）

因此采用**启发式管线**：注释剥离 → 模块边界 → 块结构配平 → 语句级正则。
代价是表达能力受限，收益是零依赖、对残缺代码鲁棒、行号精确。

### 3.2 管线细节

**① 注释剥离必须保行号**
逐字符状态机（`in_line` / `in_block` / `in_str`）把注释替换为等长空格，
保留所有换行符。这样任何后续处理的行号都能直接映射回原文件，
是"行号精确"这一硬要求的实现基础。

**② begin/end 配平用词边界而非字符串匹配**
```python
re.finditer(r"(?<![\w$])(begin|end)(?![\w$])", text[start:])
```
`(?![\w$])` 自动排除 `endcase` / `endmodule` / `endfunction`，
无需维护关键字白名单。

**③ 行号取自"赋值目标出现的位置"而非"语句起始位置"**
这是踩过的坑：`case` 项内的赋值语句跨行时，
`if (state == DATA) begin\n baud_cnt <= ...` 的语句起始行与赋值行不同，
按语句起始算会产生 1~2 行偏移。改为在未剥离前缀的原始语句内直接正则定位
赋值目标，再用匹配偏移换算行号。

**④ for 循环头必须整体排除**
`for (i = 0; i < 4; i = i + 1)` 中的 `i = 0` 会被误认为时序块阻塞赋值。
实现上先扫描出所有 for 头的偏移区间，使**其内的分号不作为语句边界**，
同时**落在区间内的赋值匹配被跳过**。修复后含 for 的时序块误报归零。

**⑤ 该层可丢弃的精度**
不做表达式位宽传播、不做宏展开、不做模块层级展开 —— 这些留给路线图。

## 4. 规则层设计

### 4.1 规则注册表

```python
RULES: List[Tuple[str, str, RuleFn]] = []

@rule("R001", "推断锁存器")
def r001_inferred_latch(mod: Module, ctx: dict) -> List[Finding]:
    ...
```

每条规则是纯函数 `(Module, ctx) -> List[Finding]`，可独立单元测试、
可单独启用（`--rules R001,R003`）、异常被引擎捕获不影响其他规则。

### 4.2 误报抑制的关键技巧

误报比漏报更致命——工程师一旦被噪音打扰就会弃用工具。因此规则实现中
大量成本花在"确认这是不是真问题"上：

| 规则 | 朴素实现 | 本项目的抑制手段 |
| --- | --- | --- |
| R001 | 组合块有 if 无 else 就报 | 检查①块首是否有默认赋值 ②敏感列表是否 `@*` ③else if 链是否有终结 else |
| R002 | 两侧位宽不等就报 | 只在 RHS 是**单一标识符或字面量**时判定；表达式一律跳过；常量按**值**推断最小位宽 |
| R003 | 时序块内出现 `=` 就报 | 排除 for 循环头 |
| R005 | 读信号 ∉ 敏感列表就报 | `@*` 直接豁免；排除常量参数 |
| R008 | 声明后未再出现就报 | **两次掩码**：先抹声明（保留初始化表达式），再抹赋值左侧 |

R008 的两次掩码是最典型的例子，缺一不可：

```
只抹赋值左侧  →  声明语句里 reg [1:0] dbg_state; 的 dbg_state 被算作"被读取" → 漏报
只抹声明      →  shreg <= {.., shreg[7:1]} 的自引用被算作"只写不读"      → 误报
两次都做      →  correct
```

### 4.3 位宽检查的常量值推断

朴素做法只比较两侧声明位宽，抓不到 `reg [3:0] cnt; cnt <= 20;`（20 需 5 位）。
本项目对无显式位宽的十进制常量按**数值所需最小位宽**推断：

```python
min_width(20) = 5   >   位宽 4   →   报截断
```

这是规则引擎相对商用工具的一个补强点。

## 5. 推理层设计

### 5.1 可插拔后端

```
LLMProvider (抽象)
├── MockProvider           离线启发式裁定器（默认，零成本、可复现）
└── OpenAICompatProvider   任意 OpenAI 兼容 /v1/chat/completions
```

`OpenAICompatProvider` 仅用标准库 `urllib` 实现 HTTP 调用，不引入 SDK。
这样同一套代码既能接云端 API，也能接本地 Ollama / vLLM，
还能在完全离线环境下用启发式裁定器跑通全流程 —— **功能不因环境而降级**。

### 5.2 提示词的结构性约束

```
严格约束:
  - 只针对给定告警作答，禁止提出新的告警
  - 若证据不足以判断，必须输出 uncertain，不得臆测
  - 输出必须是合法 JSON
```

配合代码侧的 `_apply()` 只接受 `rule_id + line` 能对上的条目，
即使模型返回了不存在的告警也会被丢弃。

### 5.3 裁定语义

| verdict | 含义 | 后续动作 |
| --- | --- | --- |
| `confirmed` | 确认为缺陷 | 计入风险评分 |
| `false_positive` | 误报 | 从统计中剔除（`is_suppressed`） |
| `uncertain` | 需人工判断 | 保留但标记 |

## 6. 扩展方式

**加一条新规则**：在 `rules.py` 里用 `@rule` 装饰器写一个纯函数即可，
自动被引擎、CLI、报告层识别。

**换一个 LLM**：实现 `LLMProvider.complete(system, user) -> str`。

**加一种输出格式**：在 `report.py` 加一个 `to_xxx(result) -> str`。

## 7. 复杂度与性能

- 解析器为单遍字符扫描 + 正则，复杂度 O(n)，n 为源码字符数。
- 单文件静态分析在毫秒量级，无需缓存即可用于编辑器实时审查场景。
- 全流程零第三方依赖，冷启动无导入开销（除标准库）。

## 8. 真实代码上的误报抑制方法论

在 3 个真实开源仓库（42 文件 / 15151 行）上验证后，提炼出本项目最重要的工程经验。

### 8.1 误报比漏报致命

审查工具的可用性由**误报率**决定：报错行号不准、噪音过多，工程师会立刻弃用。
因此所有规则默认取向是 **"宁漏勿误"** —— 证据不足时一律沉默，而非输出低置信度告警。

### 8.2 五类必须显式识别的"表观问题"

真实代码里大量合法写法在静态视角下"看起来像缺陷"，必须显式建模：

| 表观问题 | 真实语义 | 识别手段 |
| --- | --- | --- |
| 多个源驱动同一信号 | `generate if/else` 互斥分支 | 标记 generate 行区间 |
| 多个源驱动同一信号 | `ifdef / ifndef` 条件编译分支 | 标记条件编译行区间 |
| 多个源驱动同一信号 | `assign x[31]=..; assign x[30:23]=..;` 位分段驱动 | 解析位选区间，判重叠 |
| 位宽不匹配 | 实例参数覆写改变了端口位宽 | 检测实例 `#(...)`，直接跳过 |
| 位宽不匹配 | 位选连接（`.addr(a[23:0])`）截取子段 | 仅接受纯标识符连接 |
| 位宽截断 | 位宽表达式含未求值参数 | 标记 `width_unknown`，跳过 |
| 位宽截断 | `sig[i]` 实为**数组元素下标**而非位选 | 声明中记录 `is_array`，按元素宽度比较 |
| 信号未被使用 | 声明在 `ifdef` 块内，使用取决于宏 | 标记 `in_ifdef`，跳过 |
| 跨时钟域未同步 | 信号本身即同步器输出 / 格雷码指针 | 命名约定启发式（`_sync` / `_gray`） |

### 8.3 语义歧义必须靠结构信息消解

最典型的案例：**`<=` 在 Verilog 中是双重语义**。

```verilog
x <= y;                  // 非阻塞赋值
if (a <= b) begin ...    // 小于等于比较
```

仅靠正则无法区分，导致 `if (long_counter_reg <= word_cnt)` 被误判为对
`long_counter_reg` 赋值，污染驱动集合、制造假多驱动告警。

**解法：用括号深度消解歧义。** 预计算每个字符位置的前缀括号深度：

- 深度为 0 ⇒ `<=` 出现在语句顶层 ⇒ 非阻塞赋值
- 深度 > 0 ⇒ `<=` 出现在括号内 ⇒ 比较运算符

同理，`for (i = 0; ...)` 循环头内的 `=` 通过"预扫描循环头偏移区间"排除。

> 这类 bug **只有真实代码能暴露**：自造样例时会有意无意避开易混淆写法。
> 这也是为什么"受控样例集满分"不能作为项目完成的标志。

### 8.4 降噪与聚合

成熟设计里调试打印（`$display` / `$error`）常达数十上百处。
逐行上报会淹没真正的问题，因此按模块聚合为一条并在消息中给出总处数。
同时按真实工程语义重新分级：`initial` 在 FPGA 流程合法（warning），
`$display` 属纯调试代码（info），只有 `#N` 延时、`while`、`fork` 才是 error。

## 9. 与同类工作的定位

调研后确认，本项目与几条并行路线的关系如下（详见 `docs/相关工作与资源调研.md`）：

| 路线 | 代表 | 缺陷发现机制 | 与本项目的关系 |
| --- | --- | --- | --- |
| 商业 / 开源 Lint | SpyGlass、Verilator、**Verible**（约 60 条规则） | 语法树 + 模式匹配 | **同源**：本项目复用其规则思路（R011 对应 Verible `always-comb-blocking`、R003 对应 `always-ff-non-blocking`），并借鉴其**外部 waiver 文件**机制 |
| LLM 直接检测 | **LintLLM**（GLSVLSI 2025，正确率 83.33%） | 逻辑树提示 + LLM 推理 | **互补**：它覆盖语法/声明类缺陷，本项目专注可综合设计缺陷；已在其**公开 benchmark** 上完成第三方实测 |
| 完整解析器 | Surelog、hdlConvertor、pysvinst | 完整 SystemVerilog 语法树 | **候选后端**：为保「零依赖」未采纳，记录为未来"高精度模式"的选项 |

**核心差异**：本项目把 LLM 从"检测器"降级为"裁定与解释器"，
用确定性规则承担缺陷发现。这个架构判断已在 LintLLM 的公开 benchmark 上
用实验验证 —— 在可综合设计缺陷类上规则有效（敏感列表 44%），
在语法/声明类上为 0%，边界清晰（见 `bench/evaluate_lintllm.py`）。

## 10. 已知技术债

1. `parser.py` 单一文件承载较多职责（词法/结构/语句/声明），
   若规则数继续增长需拆分为 `lexer.py` / `structure.py` / `decl.py`。
2. 规则函数之间存在少量重复的信号读取逻辑（如 `_read_signals` 的调用模式），
   可抽象为统一的"数据流视图"。
3. `generate` 目前仅用于抑制表观多驱动，未做分支语义展开，
   因此参数化设计下的跨模块检查仍不完整。
4. `ModuleIndex` 按文件顺序"先到先得"，遇到同一模块名的多个实现
   （不同工艺库/配置）时无法区分。
