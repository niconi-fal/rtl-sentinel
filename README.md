# RTL-Sentinel

**面向集成电路设计的 RTL 智能审查 Agent** —— 静态规则引擎负责确定性事实，
LLM 负责语义裁定与修复建议。**零第三方依赖**，一条命令即可运行。

[![RTL Sentinel Regression](https://github.com/niconi-fal/rtl-sentinel/actions/workflows/regression.yml/badge.svg?branch=main)](https://github.com/niconi-fal/rtl-sentinel/actions/workflows/regression.yml)

```
python run_demo.py
```

---

## 1. 它解决什么问题

RTL 代码审查目前依赖昂贵的商业 Lint 工具（SpyGlass、Ascent Lint 等），
且工具只报"哪里错了"，不解释**为什么错、应该怎么改**。而直接用大模型审代码
又不可靠——LLM 在位宽算术、数据流追踪这类需要精确符号计算的任务上会系统性出错。

RTL-Sentinel 的思路是把两件事拆开：

| 环节 | 承担者 | 理由 |
| --- | --- | --- |
| 找出问题 | 确定性规则引擎 | 位宽截断/多驱动是**符号计算**，必须可复现、零随机 |
| 解释与修复 | LLM | 根因归纳、代码补丁、验证方法属于语义理解 |

**关键约束：LLM 只能对规则引擎已产出的告警做裁定，不允许发明新告警。**
这一条是抑制幻觉的核心，也让 LLM 的贡献可被量化评测。

## 2. 快速开始

```bash
# 一键演示（扫描样例 -> 生成报告）
python run_demo.py

# 审查单个文件 / 整个目录
python -m rtl_sentinel.cli samples/bad/uart_tx_buggy.v
python -m rtl_sentinel.cli rtl/ -f html -o report.html

# 只跑确定性规则，不调用语义推理层（CI 流水线场景）
python -m rtl_sentinel.cli rtl/ --no-llm --min-severity warning

# 接入任意 OpenAI 兼容后端（云端 / 本地 vLLM / Ollama）
export RTL_SENTINEL_API_KEY=sk-xxx
python -m rtl_sentinel.cli rtl/ --base-url http://localhost:11434/v1 --model qwen2.5-coder

# 手动复核评测指标
python bench/evaluate.py

# 一键离线回归（受控集 + 真实语料基线 + 外部交叉验证）
python bench/run_all.py
```

环境要求：Python 3.8+，**无第三方依赖**（仅标准库）。
实测性能：7 个设计 / 363 行 RTL 全量静态分析 18.7 ms（约 2.7 ms/文件）。

CLI 退出码：`0` 无错误级告警，`1` 存在错误级告警，`2` 路径或输入异常 —— 可直接用于 CI 门禁。

## 3. 规则清单

| ID | 规则 | 严重度 | 说明 |
| --- | --- | --- | --- |
| R001 | 推断锁存器 | warning | 组合块 if/else if 链无终结 else、case 无 default、且无块首默认赋值 |
| R002 | 位宽截断 | error | 赋值两侧位宽不符；含**常量值位宽推断**，可抓出 `reg[3:0] x; x<=9;` |
| R003 | 阻塞赋值误用 | error | 时序块内对寄存器使用 `=`；已排除 for 循环头 |
| R004 | 多驱动 | error | 同一信号被多个 always 块 / 多条 assign / 实例输出同时驱动 |
| R005 | 敏感列表不完整 | warning | 组合块读取的信号未列入敏感列表（`@*` 自动豁免） |
| R006 | 跨时钟域未同步 | warning | 信号在 A 时钟域写入、B 时钟域直接采样 |
| R007 | 不可综合结构 | error | `initial`／`#N` 延时／`$display`／`while`／`fork-join` 等 |
| R008 | 未使用信号 | info | 只写不读或声明后从未被读取；条件编译块内的声明自动豁免 |
| R009 | 实例端口位宽不匹配 | error | 跨文件比对实例连接与模块端口定义（参数覆写/位选连接自动跳过） |
| R010 | 实例端口未连接 | warning | 实例化时漏连的输入端口（位置连接无法判断时跳过） |
| R011 | 组合逻辑误用非阻塞赋值 | warning | 组合块内使用 `<=`，仿真与综合行为不一致 |
| R012 | 赋值运算符误用 | error | `assign x == y;` 把赋值误写成比较，目标信号悬空 |
| R013 | 实例化连接方式混用 | error | 同一实例内混用按名与按位置连接（Verilog LRM 禁止） |

> R011–R013 来自公开 benchmark 调研（详见 `docs/相关工作与资源调研.md`），
> 对应的正是 Verible 的 `always-comb-blocking` 等工业规则覆盖的场景。

> R009 / R010 依赖**跨文件模块索引**：真实工程是多文件的，单文件分析看不到
> 被实例化模块的端口定义。索引见 `rtl_sentinel/index.py`。
> 查不到定义的模块（FPGA 原语、工艺库、第三方 IP）一律**保守不判**。

## 4. 评测结果

评测集：12 个 Verilog 设计（8 个植入已知缺陷 + 4 个干净基线，含 1 个 `for`
循环块的边界回归用例）。标注以 `GROUND TRUTH` 注释内嵌于源码首部，形如
`R004@30 R006@14 R008@17`（`@` 后为期望**行号**），保证可复现、可审计。

评测分两级（`bench/evaluate.py`）：

① **规则级** —— 判定单元 = (文件, 规则 ID)：某规则是否在该文件上触发。
② **定位级** —— 判定单元 = (文件, 规则 ID, 行号)：触发位置是否正确、是否
   漏报或重复上报。**这一级是“行号精确”这一硬约束的回归防线** —— 旧
   口径只查第①级，行号全写错、同一问题重复报十次也照样拿满分。

```
① 规则级   TP=24  FP=0  FN=0   Precision=100.0%  Recall=100.0%  F1=1.0000
② 定位级   TP=35  FP=0  FN=0   Precision=100.0%  Recall=100.0%
```

定位级立刻暴露过一处规则级看不见的问题：`bad/uart_tx_buggy.v` 的 `R004`
实际有**两处**（`busy` 与 `dbg_pulse` 各被两个源驱动，L50 / L70）；规则级
只算一次、无法察觉，定位级把两处分别校验。

**关于 100% 的说明（重要）**：该指标来自**自建受控样例集**——缺陷位置由人工
精确植入并标注，用于验证规则逻辑的正确性与零误报特性，**不代表在真实工程代码
上的表现**。真实代码上的泛化验证是下一步工作（见第 7 节）。

干净基线的价值在于度量**误报率**：审查工具一旦误报率高，工程师会直接放弃使用。

## 4.2 真实代码泛化验证

受控样例集只能证明"规则逻辑写对了"，不能证明"在真实代码上能用"。
因此引入 3 个真实开源仓库（共 **42 文件 / 15151 行**，来源与 license 见
`bench/corpus/SOURCES.md`）做泛化验证。首轮结果暴露了 **7 类系统性误报**：

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| R004 报 215 条多驱动 | 把实例的**所有**端口连接当驱动源，未查端口方向 | 建立跨文件模块索引，仅 output/inout 计入驱动 |
| R004 仍报参数化分支 | `generate if/else` 是互斥分支，静态看像多驱动 | 标记 generate 区间，互斥分支不计 |
| R004 误报分段驱动 | `assign x[31]=..; assign x[30:23]=..;` 是合法的位分段驱动 | 解析位选区间，无重叠则不报 |
| R009 大量误报 | 参数覆写实例（`#(.W(32))`）改变了端口位宽；位选连接被当作整信号 | 两类情形保守跳过 |
| R002 报位宽截断 | 位宽表达式含未求值参数时退化为 1 位 | 标记"位宽未知"，跳过而非误判 |
| R002 误报数组元素 | `axis_tdata_pipe[0]` 的 `[0]` 是**数组下标**而非位选（语法完全相同） | 声明中记录数组维度以区分 |
| R008 报调试寄存器 | `ifdef DEBUGREGS` 内的声明使用与否取决于宏 | 标记条件编译区间，自动豁免 |
| R003 报 45 条 | picorv32 刻意用阻塞赋值做块内顺序计算 | 降为 warning，消息说明属风格差异 |

以及一个**解析器真实缺陷**：`if (a <= b)` 中的"小于等于"被误认成非阻塞赋值
（`<=` 在 Verilog 中双重语义）。修复方案是用**括号深度**区分——语句顶层是赋值、
括号内是比较。修复后 R004 从 215 条降到 8 条。

**收敛结果**

| 指标 | 首轮 | 修复后 | 变化 |
| --- | --- | --- | --- |
| 告警总数 | 491 | **127** | −74% |
| error 级 | 397 | **27** | **−93%** |
| R004 多驱动 | 215 | 8 | −96% |
| R002 位宽 | 59 | 13 | −78% |
| R007 不可综合 | 111 | 34 | 重新分级 + 按模块聚合 |
| R006 跨域 | 9 | 1 | 识别同步器/格雷码约定 |

受控评测集在每一轮修复后都做了回归：**始终 24/24（R001–R013 全覆盖）、Precision 100%、Recall 100%**。

剩余 8 条 R004 全部来自 `spiflash.v`（SPI Flash 行为仿真模型，非综合目标），
1 条 R006 与 2 条 R001 亦为仿真模型 / 需结合设计意图判断的合理提示。

## 4.3 语义推理层的裁定评测

规则层负责"发现问题"，语义推理层负责"裁定真伪"。后者的能力此前从未被量化，
因此用人工复核得到的金标准（`bench/golden_adjudication.json`，43 个
(文件, 规则) 组合 / 127 条告警）度量其裁定准确率。

裁定标准：**该告警是否指向一个需要修改的真实问题**。
对成熟开源项目而言，"技术上正确但设计者有意为之"应判为 `false_positive`（需豁免）。

| 推理后端 | 一致率（判定单元，42 个） | 一致率（告警条数，旧口径） | 「应豁免」类 | 「无法判定」类 |
| --- | --- | --- | --- | --- |
| 朴素启发式（默认判 confirmed） | — | 12.7%※ | — | — |
| 离线启发式（无网络环境） | **85.7%** (36/42) | 90.6% (115/127) | 88.1% | **100%** |
| **DeepSeek**（真实 LLM） | **73.8%** (31/42) | 89.0% (113/127) | **99.0%** | 53.8% |

> **口径说明（重要）**：金标准是“每个 (文件, 规则) 一个结论”，而同一组合可对应多点告警。
> 旧口径按**告警条数**计数，会把同一个标注重复计入多次（42 个独立标注被算成 127 条），
> **系统性抬高数字**；请以**判定单元**口径为准。后两列（应豁免类 / 无法判定类）仍为告警条数口径。
>
> 另需注意：该金标准目前是**“自产自评”**（本项目自己标注、再评测自己），属循环论证，
> 是本项目已知的最大方法论短板。独立盲标流程见 `docs/项目说明.md` 第十一节。
>
> 第十一节还给出一次**标注者一致性实验**：同一批 42 题换标注者（不同模型 / 不同提示词），
> 与工具的一致率落到 **45%–50%**，标注者彼此一致率 **47.6%–95.2%** —— 说明这个指标
> 由**标注者**主导，而非工具的固有属性。因此本项目不主张单一一致率数字。
> （另：工具侧在该语料上只给出 2 条 `confirmed`（`axis_ll_bridge.v` 的 R003 —— 也正是
> 两个独立标注模型在二元协议下**唯一共同判 change** 的条目）；改用**二元协议**后，
> 标注者彼此一致率从 **47.6% 提升到 83.3%**；详见 `docs/项目说明.md` 第十一节。）
> （进一步实验：给出文件级事实后两模型决策不变 —— 剩余分歧源于“仿真模型是否在
> 审查范围内”的标准不同，提示词已补上范围定义；详见同节。）
> 详见 `docs/项目说明.md` 第十一节。）

※ 朴素启发式那行的口径为 126 条告警的早期版本，列出以说明“默认硬判 confirmed”的代价。
LLM 存在非确定性，多次实测（告警条数口径）在 **88–90%** 之间波动；离线后端则完全稳定。

```bash
# 离线后端（默认，零成本、可复现）
python bench/evaluate_adjudication.py

# 接任意 OpenAI 兼容后端
RTL_SENTINEL_API_KEY=sk-xxx python bench/evaluate_adjudication.py \
    --model deepseek-chat --base-url https://api.deepseek.com/v1
```

### 真实 LLM 实测带来的关键发现

接入 DeepSeek 后一致率**并非单调提升**，但拆开看差异极具说明性：

- **LLM 在"语义豁免判断"上明显更强（99.0% vs 88.1%）** —— 判断一段代码是
  "有意为之"还是"笔误"，正是语义理解的用武之地，实验证实了这一点。
- **离线硬规则在"承认无法判定"上更强（100% vs 46.2%）** —— 因为离线后端被
  明确编程为"判不了就标 uncertain"，而 LLM 倾向于给出结论。
- 按**判定单元**口径，离线后端（85.7%）反而**高于** DeepSeek（73.8%）—— 差异集中在
  「该不该下结论」的保守度上：LLM 更倾向给出结论，把人工标 `uncertain` 的判成
  `false_positive`；旧口径因重复计权把这一差异抹平了。

这验证了本项目的分工设计：**规则层的确定性事实 + LLM 的语义判断是互补的**，
而不是简单替代关系。

> 一个诚实的补充：那 14 条"人工标 uncertain、LLM 判 false_positive"的差异中，
> 多数（如 axis 库未使用信号、`pause_req` 未连接）**人工标注可能偏保守**，
> LLM 的判断反而更明确。也就是说 LLM 的真实优势被这份金标准**低估**了。

**上下文供给决定 LLM 表现**（一个重要的工程经验）：首轮只给单行代码时，
DeepSeek 一致率只有 **40.9%**，低于离线后端；补上"告警行附近的源码上下文 +
文件性质（是否仿真模型）+ 规则层语义标记"后提升到 **88.2%**。
**接上大模型不等于变好，喂什么上下文才是决定性的。**

**关键认识**：在成熟工程代码上，规则告警的绝大多数（**79%**）**并非需要修复的缺陷**，
而是需要豁免的合法写法（行为仿真模型、块内临时变量、有意位宽截断、仿真断言）。
因此裁定层的正确姿态是 **"能判的判，判不了的交出去"** ——
不具备语义理解能力却硬判 confirmed，会让工具彻底失去豁免能力。

离线后端可明确判定的三类：

1. **行为仿真模型**——含 `#N` 延时与 `task` 定义（非综合目标，其告警无工程意义）
2. **块内临时变量的阻塞赋值**——未被其他块/连续赋值/实例连接引用，属风格而非缺陷
3. **仿真调试代码与断言**——`$display` / `$error` / `$fatal`，综合工具直接忽略

其余 11 条（全部为 R002 的"有意截断"，如 32 位 `gpio` 驱动 8 位 LED）
如实标为 `uncertain` —— 这类问题需要设计意图判断，正是真实 LLM 的价值所在。

## 4.4 第三方基准：LintLLM benchmark

为避免"自己出题自己考"，引入了 GLSVLSI 2025 论文 **LintLLM** 的公开 benchmark
（90 个 Verilog 模块 × 11 类注入缺陷，MIT 许可）做第三方评估：

```bash
python bench/evaluate_lintllm.py
```

**结果**

```
模块级检出率 : 23.3%  (21/90)
告警精确率   : 27.5%

Sensitivity List 44% │ Module Instances 38% │ Reserved words 33% │ Operators 29%
Port Type 25% │ Signal Usage 23% │ Bit Width Usage 21% │ Race or Hazard 9%
Syntax Structure 0% │ Logic Synthesis 0% │ Combinational or Sequential 0%
```

**结论**：本工具在**可综合设计缺陷**上有效，在**语法与声明类**缺陷上基本无覆盖 ——
这与 LintLLM（让 LLM 直接做检测，正确率 83.33%）形成**互补而非竞争**关系，
完整分析见 `docs/相关工作与资源调研.md`。

该 benchmark 也暴露出一个真实盲区：**Bit Width Usage 初测仅 14%**，
根因是 R002 对表达式一律跳过，而 Verilog 的算术运算**不会自动扩位**
（`a + b` 的结果位宽是 max(width(a),width(b)) 而非 max+1，
所以 `reg [3:0] sum; assign sum = a + b;` 会静默丢失高位）。
补上保守的表达式位宽推断后提升到 21%。

> **需要说明的局限**：该 benchmark 每个模块只标注"注入的那一处"缺陷，
> 未标注代码中自然存在的其他问题。因此任何检出额外问题的工具都会被计入"误报"
> （Verilator 32.22% 的误报率有同样成因）。本工具 27.5% 的精确率被显著低估。

## 4.5 对照实验：LLM 直接检测 vs 规则引擎

为了检验"可形式化的缺陷是否真的更适合规则引擎"，做了**同 benchmark、同口径**的
对照实验：让 DeepSeek 直接读源码指出缺陷行（零提示工程，温度 0），
与规则引擎的结果对比。

```bash
RTL_SENTINEL_API_KEY=sk-xxx python bench/evaluate_llm_direct.py \
    --model deepseek-chat --base-url https://api.deepseek.com/v1
```

| 方案 | 模块级检出率 | 来源 |
| --- | --- | --- |
| 商业 EDA | 64.44% | 上游论文 |
| Verilator | 62.22% | 上游论文 |
| o1-mini + LintLLM（带逻辑树提示） | 83.33% | 上游论文 |
| **DeepSeek 直接检测（零提示工程）** | **72.2%** | 本次实测 |
| RTL-Sentinel 规则引擎 | 23.3% | 本次实测 |

### 这个结果该怎么读

**在"缺陷定位检出率"这个单一指标上，DeepSeek 显著优于规则引擎。**
我们如实记录这一点，并给出三点分析：

**① 任务的适配性差异。** 该 benchmark 侧重语法与声明类缺陷（中文标点、
未声明信号、保留字误用）—— 这类"读一遍就能发现"的问题，LLM 天然占优；
规则引擎要为每种模式手写规则，成本高。DeepSeek 在 Syntax Structure 上拿到 83%，
而规则引擎是 0%，就是这个原因。

**② 复杂度带来的衰减方向不同。**

| 难度 | DeepSeek | 规则引擎 |
| --- | --- | --- |
| simple | **96.7%** | 23.3% |
| medium | 86.7% | 16.7% |
| complex | **33.3%** | **30.0%** |

代码越长，LLM 的注意力衰减越明显（96.7% → 33.3%）；
而规则引擎**不受代码长度影响**（30% 反而是它最高的一档）。
这体现了确定性分析的长度鲁棒性。

**③ 工程指标上的取舍完全不同。**

| 维度 | DeepSeek 直接检测 | 规则引擎 |
| --- | --- | --- |
| 90 模块耗时 | 81.8 s | **18 ms（快 4500 倍）** |
| 成本 | 约 ¥0.1–0.3 | **0** |
| 可复现性 | 温度 0 也不保证逐字一致 | **完全确定** |
| 输出可审计 | 自然语言，需人工复核 | **结构化，可进 CI 门禁** |
| 受控集精确率 | — | **100%** |

**结论：两者不是替代关系，而是分层关系。**
LLM 适合**探索式审查**（高覆盖、需人工复核、可接受成本与延迟）；
规则引擎适合 **CI 门禁**（零误报、毫秒级、可复现、可审计）。

### 基于此结论落地的功能：`--llm-detect`

既然实验证明 LLM 检出率更高，项目实现了**大模型检测通道**作为规则引擎的补充：

```bash
python -m rtl_sentinel.cli rtl/ --llm-detect -f html -o report.html
```

三条硬约束（保证不破坏可复现性）：

1. 输出一律标记 `needs_review`，在报告中显示为「待复核 · LLM 线索」
2. severity **强制为 info**
3. **不计入风险分**，因此不影响 CI 门禁

实测（受控样例集（当时 9 文件，现为 12 文件））：规则引擎 32 条 → 规则 + LLM 通道 63 条
（补充 31 条线索），**风险分保持 100.0 不变**。
补充的线索质量可用 —— 例如它准确指出 `fsm_buggy.v L23`"else-if 链无终结 else，
S_DONE 时 nstate 无赋值，推断 latch"，与规则 R001 结论一致。

## 4.6 外部交叉验证：用 Verilator 独立复核

前面几节的评测都是“自证”。为引入**外部权威工具**的独立证据，新增
`bench/check_verilator.py`：对同一批样例跑 Verilator `--lint-only`，与本工具交叉
核对；该脚本同时接入了 CI（`.github/workflows/regression.yml`）。

**实测口径（重要：两者的重叠是部分重叠）**

| Verilator 警告 | 对应本工具 | 能否作缺陷信号 |
| --- | --- | --- |
| `LATCH` | R001 推断锁存器 | 是 |
| `MULTIDRIVEN` | R004 多驱动 | 是；但连续 `assign` 重复驱动 Verilator 不报，此时本工具覆盖更广 |
| `WIDTHTRUNC` / `WIDTHEXPAND` | R002 位宽 | **否** —— Verilator 5 无笼统 `WIDTH`；`WIDTHEXPAND` 是正常零扩展，干净基线也会触发 |
| `%Error-BLKANDNBLK` | R003 阻塞/非阻塞混用 | 是（Verilator 直接判为 Error） |

**验收标准（版本无关）**：① 干净基线不得出现 `LATCH`/`MULTIDRIVEN`；
② 缺陷样例中这些码至少被佐证一次。

**实测结果**：4 个干净基线全部零缺陷码；`inst_buggy` 被独立佐证 `MULTIDRIVEN`，
`fsm_buggy` 被佐证 `BLKANDNBLK`。个别样例 Verilator 无法完成 lint（含其不支持的
语法），脚本会打印 `[SKIP]` 及原因，不计入判定。

                                 ▼

解析器采用**启发式管线**而非完整 IEEE 1364 语法分析，取舍理由：

精度足以支撑全部 13 条规则。代价是放弃了对完整语法树的表达能力。

## 5.2 豁免机制与 CI 集成

**豁免（waiver）**：真实项目必然存在"命中规则但设计者有意为之"的代码
（实测占成熟开源代码告警的 **79%**）。没有官方豁免通道，工程师只能关掉整条规则、
或在报告里人工忽略，最终导致工具被弃用。

RTL-Sentinel 提供集中式、**强制带理由、可审计**的豁免配置 `.rtlsentinel.json`：

```json
{
  "waivers": [
    {"file": "spiflash.v", "rule": "R004", "reason": "行为仿真模型，非综合目标"},
    {"file": "picorv32.v", "rule": "R003", "lines": [1406, 1407],
     "reason": "块内顺序计算风格"},
    {"file": "axis_*.v",   "rule": "R007", "reason": "AXI 库的仿真断言"}
  ]
}
```

字段均可选（缺省匹配全部），`reason` 必填以保证每条豁免可审计。

**设计原则：豁免不隐藏。** 被豁免的告警仍会出现在报告中，只是单独归入"已豁免"区
并注明理由；在 SARIF 中以 `suppressions` 形式保留 —— 避免豁免演变成问题藏匿手段。

实测效果（真实语料 42 文件 / 15151 行，`bench/corpus/.rtlsentinel.json`）：

| | 告警数 | 风险分 | 健康分 |
| --- | --- | --- | --- |
| 未豁免 | 127 | 83.0 | 17.0 |
| 应用 14 条豁免规则 | **33** | **20.1** | **79.9** |

**风险分按代码规模归一化**：绝对加权和对大工程不公平 —— 15000 行代码里的 8 个 error
与 200 行里的 8 个 error 严重程度完全不同。基准为「每千行 40 个加权缺陷 = 满风险」。

**CI 集成**：`.github/ci-examples/rtl-sentinel.yml` 提供 GitHub Actions 示例，
结果经 SARIF 上传到 Code Scanning，在 PR 中以行内批注展示：

```bash
python -m rtl_sentinel.cli rtl/ -f sarif -o rtl-sentinel.sarif --no-llm

# 门禁：退出码 1 = 存在 error 级告警（已豁免的告警不计入）
python -m rtl_sentinel.cli rtl/ --no-llm --min-severity error
```

## 7. 局限与路线图

**已知局限**（主动披露）

1. 解析器覆盖 Verilog-2001/2005 常用子集，不支持 UDP 原语、`generate` 宏展开、
   完整 SystemVerilog 类与断言语法。
2. R006 只做**同模块内跨时钟域**检测，跨模块 CDC（需建立时钟树与模块层级视图）未覆盖；
   且依赖命名约定（`_sync` / `_gray`）识别已同步信号，属启发式判断。
3. R002 的位宽推断基于声明位宽与字面量，不做完整的表达式位宽传播。
4. R003 对"用阻塞赋值做块内顺序计算"的编码风格（如 picorv32）会命中，
   属设计风格差异而非缺陷，已降为 warning。
5. R009 对带参数覆写的实例不做判断（无法确定覆写后的端口位宽）。
6. 离线裁定器用规则化先验模拟语义判断，不等价于真实 LLM 的语义理解能力。
7. 解析器符号覆盖有量化缺口：声明若落在 `generate` / `ifdef 区间内便进不了符号表，使
   R002/R003/R008 等**静默跳过**（实测 11/64 模块、59/1563 赋值目标受影响 = 3.8%）；
   已加 `bench/check_symbol_coverage.py` 作回归棘轮，彻底修复需改走未屏蔽文本。

**路线图**

- [x] 在开源 RTL 仓库上做增量验证，度量真实误报率（error 397 → 27，见第 4.2 节）
- [x] 引入外部权威工具交叉验证：Verilator 独立佐证 R003（BLKANDNBLK）/ R004（MULTIDRIVEN），见第 4.6 节
- [x] 真实 bug 回溯验证：`axis_pipeline_fifo` 的阻塞赋值缺陷，修复前命中 R003、修复后消失
      （并因此查出并修复了 R003 的一处静默漏报；见 `docs/项目说明.md` 第十二节）
- [ ] 建立 LLM 裁定 vs 人工标注的一致性评测，量化语义推理层带来的准确率增益
- [ ] `generate` 分支语义展开，支持参数化设计的完整跨模块检查
- [ ] 跨模块 CDC 检测（需建立时钟树与模块层级视图）
